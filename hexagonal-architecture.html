Hexagonal Architecture
업무의 안과 밖을 Port로 연결합니다.

업무 기능을 애플리케이션 핵심에 두고, 화면·DB·메시지 같은 외부 기술을 Port와 Adapter로 연결하는 구조입니다.

PORTS & ADAPTERS

핵심은 업무를 표현하고, 어댑터는 외부 기술을 번역합니다.

Hexagonal Architecture는 Alistair Cockburn이 설명한 Ports & Adapters 아키텍처입니다. UI나 DB를 먼저 중심에 두기보다, 애플리케이션이 제공하는 기능과 외부에 요구하는 능력을 경계의 계약으로 드러냅니다.

구성담당하는 일주문 처리 예시
애플리케이션 핵심유스케이스를 수행하고 업무 규칙을 지킨다.PlaceOrderService와 Order·OrderLine·Money
입력 Port애플리케이션이 외부에 제공하는 작업을 정의한다.PlaceOrder.execute(command)
Driving Adapter외부 입력을 입력 Port 호출로 변환한다.REST Controller, CLI, 메시지 Consumer, 테스트
출력 Port업무 처리를 위해 외부에 요구하는 능력을 정의한다.OrderRepository, PaymentAuthorizer
Driven Adapter출력 Port를 특정 기술로 구현한다.PostgresOrderRepository, 결제 API Client
PORT의 의미

Port는 네트워크 포트 번호가 아니라 의미 있는 대화의 계약입니다. 한 Port에 여러 Adapter를 연결할 수 있습니다.

왜 육각형인가요? Port가 여섯 개 있어야 하나요?

육각형은 안쪽과 바깥쪽, 여러 연결 지점을 시각적으로 드러내는 표현입니다. 여섯 변이나 여섯 Port가 필수라는 뜻은 아닙니다. 이 문서는 한국어 레이블을 읽기 쉽게 사각형 경계로 표현합니다.

입력·출력은 네트워크 데이터의 이동 방향보다 누가 기능을 시작하고 누가 외부 기능을 제공하는지를 가리킵니다. 조회용 Repository도 애플리케이션이 호출하는 Driven 쪽입니다.

DEPENDENCY INVERSION

실행이 바깥으로 가도, 핵심의 의존성은 안쪽 계약에 머뭅니다.

의존성 역전 원칙(DIP)은 업무 정책이 외부 기술의 구체 구현에 묶이지 않도록 의존 관계를 설계하는 원칙입니다. 의존성 주입(DI)은 그 설계를 실행할 때 필요한 구현 객체를 전달하는 방법입니다. DI Container는 선택 사항입니다.

입력 Port와 출력 Port의 구현 주체는 어떻게 다른가요?

입력 Port인 PlaceOrder는 핵심의 Use Case가 구현하고, Controller가 호출합니다. 출력 Port인 OrderRepository는 핵심이 요구하는 계약이고, 바깥의 DB Adapter가 구현합니다. 두 경우 모두 바깥 코드가 안쪽의 계약을 알아야 합니다.

Port는 인터페이스 클래스로 표현할 수 있지만 함수 타입·프로토콜·모듈 API로도 표현할 수 있습니다. 유스케이스마다 인터페이스 파일을 하나씩 만들라는 규칙은 아닙니다.

주문 생성의 실행 흐름

입력 변환, 업무 판단, 저장 구현이 각자 책임을 가집니다.

작은 의사 코드로 보면 어떻게 연결되나요?
interface PlaceOrder {
  execute(command: PlaceOrderCommand): PlaceOrderResult
}
interface OrderRepository {
  save(order: Order): void
}
class PlaceOrderService implements PlaceOrder {
  constructor(private orders: OrderRepository) {}
  execute(command) {
    const order = Order.place(command.customerId, command.lines)
    this.orders.save(order)
    return { orderId: order.id, status: order.status }
  }
}
const orders = new PostgresOrderRepository(database)
const placeOrder = new PlaceOrderService(orders)
const controller = new OrderController(placeOrder)

타입·동기 처리·트랜잭션 표현을 단순화한 의사 코드입니다. 마지막 조립 코드는 외부 구성을 아는 Composition Root에 둡니다. 실제 구현에서는 저장 실패, 중복 요청, 동시성, 커밋 경계를 명시합니다.

기술과 독립적인 검증

DB 없이 업무를 검증하고, 실제 기술의 계약도 따로 확인합니다.

경계에서 다루어야 할 것

인터페이스를 추가한 뒤에도 데이터와 실패의 의미를 설계해야 합니다.

Repository 하나에 모든 저장 기능을 넣어도 되나요?

Port는 애플리케이션의 대화 목적을 드러내야 합니다. 모든 테이블과 CRUD를 담는 거대한 인터페이스보다 업무가 요구하는 능력으로 경계를 나누는 편이 읽기 쉽습니다. 반대로 단순한 동작까지 과도하게 추상화하면 코드 탐색과 변경 비용이 늘어납니다.

적용 판단

업무 규칙이 오래 유지되고 외부 기술·입력 경로가 바뀔 때 유용합니다. 단순 CRUD라면 경계가 줄이는 변경 비용과 추가 추상화 비용을 함께 봅니다.
