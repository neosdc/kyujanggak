OBSERVABILITY · OPENTELEMETRY + JAEGER

OpenTelemetry + Jaeger
요청의 경로를 기록하고, 지연을 추적합니다.

OpenTelemetry는 관측 데이터를 만들고 보내는 기반입니다. Jaeger는 Trace를 저장·조회하는 플랫폼입니다. 두 도구를 연결하면 여러 서비스에 걸친 한 요청의 흐름을 살펴볼 수 있습니다.

두 도구의 역할

계측·전송과 Trace 저장·조회가 이어집니다.

구성 요소담당하는 역할실제로 결정할 것
OpenTelemetry · OTelTrace·Metric·Log 등의 생성·수집·전송을 위한 규격·API·SDK·도구 모음사용 언어와 프레임워크의 계측, 데이터 계약과 전송 방식
OTel API · 계측 라이브러리작업·측정을 기록하는 호출과 공통 라이브러리 연동HTTP·DB 자동 계측, 업무 구간의 수동 계측
OTel SDKAPI의 구현, Context·샘플링·처리·Export 구성서비스 식별 정보, Span 처리기와 Exporter
OTel Collector프로세스 밖에서 데이터를 받아 처리하고 목적지로 전송수신 프로토콜, 가공·배치·필터·전송 파이프라인
Jaeger분산 Trace의 수집·저장소 연계·검색·시각화저장소, 보관 기간, 수집과 조회의 배포·운영

OpenTelemetry는 특정 관측 백엔드에 종속되지 않는 데이터 생성·전송 기반을 제공합니다. 자체적으로 장기 저장과 대시보드 전체를 제공하는 서비스는 아니므로, 보낼 목적지와 운영 구성을 선택합니다.

이 문서는 Jaeger v2를 기준으로 설명합니다. Jaeger v2 자체도 OpenTelemetry Collector 프레임워크를 기반으로 합니다. 앞에 별도 OTel Collector를 두는 것은 공통 데이터 가공이나 여러 목적지로의 전송 등을 위한 선택입니다.

OpenTelemetry와 Jaeger를 반드시 함께 사용하나요?

OpenTelemetry가 만든 Trace를 다른 호환 백엔드로 보낼 수도 있습니다. Jaeger는 OTLP로 Trace를 받을 수 있으므로, OTel SDK에서 Jaeger로 직접 전송하는 구성도 가능합니다.

데이터 형식과 계측 코드를 표준화해도 백엔드의 검색 기능·대시보드·보관 정책까지 모두 같아지지는 않습니다. Jaeger 전용 SDK나 별도 Agent를 필수 전제로 삼기보다 OTel 계측과 OTLP를 중심으로 구성을 읽으면 좋습니다.

관측 데이터의 종류

Metric·Log·Trace가 서로 다른 질문에 답합니다.

신호알아보는 것주문 시스템의 예
Metrics · 수치 측정·집계현재와 시간에 따른 시스템의 전체적인 상태요청률, 오류율, 지연 분포, 큐 적체
Logs · 기록특정 시점에 남긴 세부 사실과 진단 정보재고 확인 실패 사유, 외부 API 응답 분류
Traces · 작업의 연결한 작업이 어떤 경로와 하위 작업을 거쳤는지주문 API → 재고 API → DB의 호출·대기 흐름

Metric으로 이상 징후를 찾고, 관련 Trace로 느린 경로를 좁힌 뒤, Log에서 자세한 맥락을 확인할 수 있습니다. Trace ID·Span ID를 로그에 연계하면 같은 실행 구간의 기록을 찾기 쉬워집니다. 로그 연계 기능은 언어·로깅 도구의 설정을 확인합니다.

이 문서에서 Jaeger가 담당하는 중심 데이터는 Trace입니다.
OTel이 지원하는 모든 Metric과 Log를 Jaeger 하나에 보내서 저장·분석하는 구성으로 이해하면 안 됩니다.

Metric·Log에는 각 신호를 처리하는 백엔드를 선택합니다. Jaeger의 서비스 성능 지표 기능처럼 Span에서 수치를 만드는 구성도 있지만, 별도의 집계·저장 경로가 필요하며 일반적인 Metric·Log 백엔드를 모두 대체하는 의미는 아닙니다.

TRACE · SPAN

Trace는 연결된 작업이고, Span은 그 안의 작업 구간입니다.

용어의미그림에서 읽는 방법
Trace ID연결된 Trace를 식별하는 값같은 Trace T에 속한 Span들을 묶음
Span ID · Parent Span ID현재 작업과 그 부모를 식별S4의 부모는 원격 호출을 보낸 CLIENT Span S3
Span Kind작업이 통신에서 맡는 역할요청 수신 SERVER, 외부 호출 CLIENT 등
Attributes작업·대상·결과를 설명하는 구조화된 값HTTP 경로·메서드, 안전하게 제한한 업무 분류 등
Span Event · StatusSpan 안의 시점 기록과 작업 결과 상태예외 기록, 특정 처리 시점, ERROR 상태 등
Resource데이터를 생성한 서비스·인스턴스의 식별 정보service.name, service.version, 배포 환경 등

부모 Span의 지속 시간은 하위 호출을 기다린 시간도 포함할 수 있습니다. 겹치는 모든 Span의 시간을 더해서 사용자 응답 시간을 구하면 안 됩니다. Trace에 보이는 지속 시간이 모두 CPU 실행 시간인 것도 아닙니다.

그림에서는 재고 호출 안의 DB 작업이 긴 구간을 차지합니다. 이를 조사 후보로 삼고 DB 지표·로그·실행 계획 등과 함께 원인을 확인합니다. Trace 한 건만으로 항상 시스템 전체의 대표 병목을 확정할 수는 없습니다.

Trace는 항상 요청 하나와 정확히 같나요?

동기 HTTP에서는 요청 하나를 출발점으로 설명하기 쉽습니다. 실제로는 배치·메시지·백그라운드 작업도 Trace의 시작이 될 수 있습니다. 비동기 처리에서는 하나의 부모 관계 외에 Span Link로 인과관계를 표현할 수도 있습니다.

Span은 계측된 작업 구간입니다. 함수·스레드·패킷 모두를 자동으로 기록하는 프로파일러가 아니므로, 필요한 구간에 계측이 있어야 합니다. Trace ID는 일반적으로 16바이트, Span ID는 8바이트 값이며 위의 T·S 표기는 학습용 축약입니다.

CONTEXT PROPAGATION

Trace 연결은 서비스 사이에 문맥을 전달해야 유지됩니다.

송신 측의 Inject는 현재 문맥을 HTTP 헤더나 메시지 메타데이터에 넣습니다. 수신 측의 Extract는 그 문맥을 읽어 새 Span의 부모 관계 등에 사용합니다. 스레드·비동기 태스크 안에서는 활성 Context를 올바르게 유지해야 합니다.

traceparent:
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

version - trace-id - parent-id - trace-flags

W3C Trace Context 형식의 예시입니다. parent-id에는 전파하는 문맥의 Span ID가 들어갑니다. HTTP CLIENT Span이 생성되는 구성에서는 해당 CLIENT Span이 원격 SERVER Span의 부모가 됩니다. 샘플링 플래그가 있어도 모든 데이터의 최종 저장을 보장하지는 않습니다.

Context 전파와 OTLP 전송은 다른 경로입니다. 전자는 업무 요청에 인과관계 정보를 싣고, 후자는 생성된 관측 데이터를 수집기로 보냅니다. 모든 SDK가 같은 수집기에 전송해도 문맥 전파가 빠지면 Trace가 자동으로 연결되지는 않습니다.

Baggage나 업무 ID는 Trace ID와 같나요?

Baggage는 Context와 함께 전달할 수 있는 키·값 정보입니다. Span Attribute에 자동으로 저장된다고 가정하면 안 됩니다. 인증 정보나 개인정보를 담기보다 필요한 공개 범위를 제한합니다.

주문 ID·메시지 ID·업무 Correlation ID와 Trace ID는 목적이 다릅니다. 하나의 주문이 여러 요청·Trace에 걸칠 수 있으므로 업무 ID는 별도 값으로 관리합니다. 외부 입력의 추적 헤더를 인증·권한의 근거로 사용하지 않습니다.

OTLP · COLLECTOR

관측 데이터의 전송과 가공을 애플리케이션 밖에서 관리할 수 있습니다.

OTLP(OpenTelemetry Protocol)는 관측 데이터를 전달하는 프로토콜입니다. 흔히 OTLP/gRPC나 OTLP/HTTP를 사용합니다. SDK의 Exporter, Collector의 Receiver, 다음 목적지의 프로토콜·주소·TLS 설정을 서로 맞춥니다.

구성하는 일설계할 내용
Receivers외부의 관측 데이터를 수신수신 주소·프로토콜·인증·지원 신호
Processors데이터를 배치·필터·수정·제한 등으로 처리처리 순서, 민감 정보 제거, 메모리·누락 영향
ExportersJaeger 등 목적지로 데이터를 전송전송 주소·프로토콜·재시도·전송 대기열
Service pipelines신호별 Receiver·Processor·Exporter를 연결구성 요소를 선언하는 것과 파이프라인에서 사용하는 것을 구별

별도 Collector를 두면 목적지·공통 가공·인프라 속성 부여를 중앙에서 관리할 수 있습니다. 동시에 Collector 자체의 가용성·용량·메모리·재시도·전송 대기열을 운영해야 합니다. Agent·Sidecar 형태로 앱 가까이에 두거나, Gateway 형태로 공유할 수 있습니다.

포트와 주소를 읽을 때 무엇을 구별하나요?

OTLP의 일반적인 기본 포트는 gRPC가 4317, HTTP가 4318입니다. HTTP의 Trace 전송에는 일반적으로 /v1/traces 경로를 사용하며, SDK의 공통 Endpoint 설정이 이 경로를 붙이는지는 해당 설정의 규칙을 확인합니다.

Jaeger UI의 일반적인 포트인 16686은 OTLP 전송 포트와 용도가 다릅니다. 포트·활성화 여부는 배포 설정에 따라 바뀔 수 있습니다. 컨테이너 안의 localhost는 그 컨테이너 자신을 가리키므로 실제 수집기 주소와 구분합니다.

Collector를 추가하는 것만으로 데이터 무손실이 보장되지는 않습니다. 큐의 한도·저장 방식·재시도 만료·과부하·목적지 장애와 SDK의 전송 대기열을 함께 확인합니다.

수집부터 조회까지

Jaeger의 수집 역할이 쓰고, Query 역할이 읽습니다.

Jaeger v2는 한 바이너리의 설정으로 수집·조회 등 역할을 구성합니다. 개발용으로 한 프로세스에 합칠 수 있고, 운영에서는 수집과 조회를 나누어 부하·접근 정책에 맞게 확장할 수도 있습니다. 그림의 상자 수가 반드시 프로세스 수와 같지는 않습니다.

인메모리 저장은 간단한 학습·검증에 쓸 수 있지만 재시작하면 데이터를 잃습니다. 운영에서는 지원되는 저장소와 보관·삭제 정책, 인덱스·쓰기·검색 부하를 검토합니다. Collector나 Jaeger를 띄우는 것과 운영할 저장 경로를 갖추는 것은 별도의 단계입니다.

Kafka가 반드시 있어야 하나요?

아닙니다. Jaeger 수집 역할에서 저장소로 직접 쓰는 구성이 가능합니다. 별도의 버퍼링이 필요하면 Kafka와 Ingester 역할을 사용하는 배포를 선택할 수 있습니다. 이 문서의 기본 그림에는 Kafka를 두지 않았습니다.

추가 버퍼도 용량·보관·장애·중복·운영 비용을 가집니다. 업무 이벤트의 브로커와 관측 데이터 버퍼는 목적이 다르므로, 같은 기술을 쓴다는 이유만으로 같은 전달 계약을 가정하지 않습니다.

JAEGER에서 읽는 방법

느린 Trace를 찾고, 하위 Span과 속성으로 범위를 좁힙니다.

순서살펴볼 것판단할 때의 주의점
대상과 시간 범위 선택문제가 난 서비스·작업·배포 버전과 시간 범위service.name·환경이 섞이거나 시간 범위가 어긋나지 않는지 확인
후보 Trace 찾기지속 시간·작업·속성·오류 등 지원되는 검색 조건검색 조건과 기능은 Jaeger·저장소 구성에 따라 확인
타임라인과 부모 관계 보기어떤 하위 호출이 길고, 어느 구간이 포함·겹치는지전체 Span 시간을 합산하지 말고 대기·병렬·임계 경로를 구별
Span 세부 정보 확인상태·속성·예외·이벤트와 원격 호출 대상HTTP 상태와 Span Status의 대응은 계측 규칙을 따름
다른 신호와 대조같은 시점의 Metric, Trace ID로 연계한 Log샘플링된 한 Trace가 전체 트래픽을 대표하지 않을 수 있음

Jaeger는 “어느 구간을 더 조사할지” 보여 주는 도구입니다. 느린 DB 호출의 실제 이유가 락인지, 실행 계획인지, 네트워크인지까지 확인하려면 해당 시스템의 지표와 로그가 필요할 수 있습니다.

Span Event는 예외나 처리 시점 같은 한 Span 안의 관측 기록입니다. EDA에서 소비자에게 전달하는 업무 이벤트와는 역할이 다릅니다. Trace가 주문·결제의 감사 원장을 대신하는 것도 아닙니다.

EDA와 분산 추적

비동기 작업은 부모 관계나 Span Link로 인과관계를 표현합니다.

Producer가 메시지 헤더·속성에 문맥을 넣고 Consumer가 추출할 수 있어야 합니다. 메시징 라이브러리와 자동 계측이 지원하는 범위를 확인하고, Outbox·Relay·백그라운드 작업처럼 프로세스가 끊기는 지점도 점검합니다.

Span Link는 현재 Span이 다른 Span의 문맥과 관련됨을 표현합니다. 한 번에 여러 메시지를 처리하는 배치나, 오래 뒤에 실행하는 작업에서 유용할 수 있습니다. Link는 부모와 다른 관계이며, Jaeger UI에서의 표시·탐색 방식은 버전과 기능을 확인합니다.

Outbox를 사용할 때 업무 요청의 인과관계를 유지하려면 전파할 문맥을 영속 기록에 함께 보관하고, Relay나 Consumer가 어떻게 사용할지 정할 수 있습니다. 이 문맥은 재전달을 막는 멱등 키가 아니며, 재시도·재처리의 Span과 업무 ID를 구분합니다.

추적 데이터를 받았으면 메시지 처리도 성공했다는 뜻인가요?

아닙니다. OTLP 수락·Trace 저장과 업무 DB 커밋·브로커 ACK는 서로 다른 계약입니다. 관측 데이터는 샘플링·유실될 수 있으므로, 결제·주문 완료와 중복 방지는 업무 상태와 전달·멱등 처리로 보장합니다.

오래 실행되는 업무 전체를 무조건 하나의 긴 Trace로 묶기보다 작업 수명·샘플링·문맥 보관 기간을 고려합니다. 업무 Correlation ID와 Span Link를 조합해 여러 Trace에 걸친 흐름을 추적할 수 있습니다.

SAMPLING · 비용과 가시성

샘플링은 남길 Trace를 선택하고, 볼 수 있는 범위도 바꿉니다.

방식결정하는 시점과 기준확인할 제약
Head SamplingTrace·Span 시작 시점의 정보로 기록·샘플링 여부 결정나중에 생길 지연·오류를 미리 모두 알 수는 없음
Parent-based 정책부모 문맥의 샘플링 판단을 관련 Span에 반영서비스마다 다른 정책을 무작정 쓰면 일부 Span이 빠질 수 있음
Tail Sampling수집한 Span들을 모아 지연·오류 등의 조건으로 보관 대상을 판단판단 대기 시간·메모리·늦게 도착한 Span·Trace별 데이터 집결을 설계

Tail Sampling을 써도 SDK에서 이미 버려 전송하지 않은 Span을 복원할 수는 없습니다. 어떤 데이터를 어디까지 보내고 어디서 선택할지 전체 경로를 설계합니다. Trace별 판단에 필요한 Span들이 같은 처리 지점에 모이는지도 중요합니다.

샘플링된 Trace 수를 곧바로 전체 요청 수나 정확한 오류율로 읽지 않습니다. 선택 정책이 오류·지연에 편향될 수 있으므로 전체 서비스 상태는 적절한 Metric과 함께 확인합니다.

많이 기록하면 항상 더 좋나요?

계측·Context 관리·직렬화·전송·저장에는 자원이 듭니다. 배치·샘플링·대기열과 실제 부하를 검증하고, 정상 종료 시 Flush 기회도 확보합니다. Collector에 버퍼가 있어도 무제한 보관은 아닙니다.

Span 이름에는 실제 주문 번호가 붙은 URL 대신 안정된 작업명이나 경로 템플릿을 사용하고, Attribute의 종류·크기·민감 정보를 제한합니다. 특히 Metric의 사용자별·주문별 Label은 시계열 수를 크게 늘릴 수 있으므로 구분해서 설계합니다.

도입 순서와 문제 해결

작은 요청 경로를 먼저 연결하고, 운영 범위를 넓힙니다.

  1. 작은 경로를 고릅니다. 주문 API에서 재고 API를 호출하는 흐름처럼 계측할 경계를 정합니다.
  2. 서비스를 식별합니다. service.name, 버전·배포 환경 등 Resource를 일관되게 설정합니다.
  3. 계측을 켭니다. 언어별 SDK 초기화 또는 자동 계측을 적용하고 HTTP·DB 계측과 업무 Span을 확인합니다.
  4. OTLP 목적지를 연결합니다. SDK에서 Jaeger로 직접 보내거나 별도 Collector를 거치는 경로를 구성합니다.
  5. 한 Trace를 검증합니다. 실제 요청을 보낸 뒤 부모 관계·시간·서비스 식별 정보를 Jaeger에서 확인합니다.
  6. 운영 정책을 추가합니다. 샘플링·민감 정보·보관 기간·수집 파이프라인의 장애·과부하·관측을 검증합니다.
증상먼저 확인할 지점가능한 원인
Trace가 전혀 보이지 않음SDK 초기화·계측·샘플러·Exporter → 수신기 → 저장소·조회SDK만 설치하고 초기화하지 않음, 프로토콜·주소·TLS·포트 불일치 등
서비스별 Trace가 따로 보임Inject·Extract, 활성 Context, 프록시·메시지 헤더전파 누락, 호환되지 않는 Propagator, 비동기 Context 손실
DB나 하위 호출 Span이 없음해당 라이브러리 계측과 버전·지원 범위미지원·비활성 계측, 샘플링·필터·전송 문제
같은 요청에 Span이 중복됨자동·수동 계측과 중복 SDK 초기화같은 라이브러리 계측을 여러 번 적용
일부 Span만 늦거나 사라짐SDK·Collector 큐, 처리 지연·드롭·저장소·보관과부하, 종료 전 미전송, Tail Sampling 대기·지연, 저장 실패
환경·서비스가 섞여 보임Resource와 검색 시간 범위·시계서비스 이름 충돌, 환경 식별 누락, 시계 오차

Monolith에서도 요청·DB·외부 API·업무 구간을 계측할 수 있습니다. Microservices에서는 서비스 경계를 넘는 Context 전파가 더 중요해지고, Micro-frontends에서는 브라우저에서 API로 이어지는 추적 범위·CORS·전파 대상 정책을 추가로 고려합니다.

관측 파이프라인에도 운영 관측이 필요합니다. SDK 전송 실패와 Collector의 수신·드롭·Export 실패, Jaeger 수집·저장·검색 지연을 확인해야 “실제 장애가 없는 것”과 “보지 못하는 것”을 구별할 수 있습니다.

이 구성을 다시 읽어 보기

Jaeger를 실행하면 모든 서비스의 호출이 자동으로 보이나요?

서비스의 계측과 전송, 경계 간 문맥 전파가 필요합니다. Jaeger는 전송되지 않은 실행 구간이나 누락된 문맥을 스스로 만들어 내지 않습니다.

모든 앱이 같은 Collector를 쓰면 같은 요청으로 묶이나요?

같은 목적지로 전송하는 것과 같은 Trace 문맥을 유지하는 것은 별개입니다. 각 요청의 문맥을 전달하고 부모·Link 관계를 맞춰야 합니다.

Trace가 없으면 업무 처리가 실패한 것인가요?

단정할 수 없습니다. 샘플링·필터·전송·보관 정책 때문에 Trace가 없을 수 있습니다. 업무의 성공 여부는 업무 상태와 결과로 확인합니다.
