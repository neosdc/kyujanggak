SOFTWARE ARCHITECTURE · EVENT-DRIVEN ARCHITECTURE

Event-Driven Architecture
발생한 사실을 알리고, 각자의 업무로 반응합니다.

이벤트 기반 아키텍처(EDA)는 구성 요소가 이벤트를 발행하고 소비하면서 협력하는 방식입니다. 주문 확정이라는 하나의 사실에 배송·알림·분석이 각자의 책임으로 반응할 수 있습니다.

EVENT · 이미 발생한 사실

이벤트는 요청의 의도와 처리의 결과를 구별합니다.

구분전달하는 의미주문 업무의 예
Command · 명령특정 책임자에게 어떤 일을 수행해 달라고 요청ConfirmOrder · 주문 확정 요청 → 검증 후 거절될 수도 있음
Event · 이벤트발행자가 책임지는 영역에서 이미 발생한 사실을 알림OrderConfirmed · 주문 확정됨 → 관심 있는 소비자가 반응
Query · 조회상태를 바꾸기보다 필요한 정보를 요청GetOrder · 현재 주문 상태 조회

메시지(Message)는 명령·이벤트 등을 운반하는 표현이나 전달 단위입니다. 큐에 넣었다는 이유만으로 명령이 이벤트가 되지는 않습니다. SendEmail은 수행 요청, EmailSent는 발송 사실로 구별할 수 있습니다.

발행자는 사실을 소유하고, 소비자는 그 사실에 대한 자기 반응을 소유합니다.
주문 확정의 판단은 주문 영역이 맡습니다. 배송 영역은 그 사실을 바탕으로 출고 준비를 결정합니다.

발행자가 소비자의 주소와 처리 순서를 직접 알 필요를 줄일 수 있습니다. 대신 이벤트의 의미·데이터 형식·발행 조건이라는 계약은 남습니다. 단순히 메서드 이름에 “Event”를 붙이는 것보다, 책임과 반응의 경계가 중요합니다.

이벤트를 받았으면 모든 업무가 성공했다는 뜻인가요?

아닙니다. 이벤트는 발행자가 확인한 사실을 나타냅니다. OrderConfirmed를 받아도 배송 준비나 안내 발송은 아직 완료되지 않았을 수 있습니다. 필요한 후속 업무의 완료는 별도 상태나 결과 이벤트로 확인합니다.

또한 소프트웨어의 모든 클릭·알림에 이벤트를 사용한다고 해서 업무 시스템 전체가 EDA로 설계되었다고 말하는 것은 아닙니다. 이 문서는 업무 구성 요소 사이의 협력을 중심으로 설명합니다.

앞선 아키텍처와의 관계

EDA는 배포 단위와 함께 선택하는 협력 방식입니다.

함께 쓰는 용어설명하는 관점EDA와 결합하면
Monolith · Modular Monolith애플리케이션의 배포 단위와 내부 업무 경계같은 애플리케이션의 모듈들이 내부 이벤트로 협력 가능
Microservices독립 배포하는 서비스의 업무 경계서비스 사이에 이벤트 발행·구독을 적용 가능
2-Tier · 3-Tier시스템을 나누는 실행·배포 계층계층 내부나 계층 사이의 일부 처리에 이벤트 적용 가능
MVC상태·업무 규칙, 화면과 입력 흐름의 책임 분리업무 처리 과정에서 이벤트를 발생시키고 처리 가능
SPA + API브라우저 앱과 백엔드 API의 역할 구분API 뒤에서 이벤트로 후속 업무를 수행 가능
Micro-frontends프런트엔드의 업무 소유·조합·배포 경계공개 UI 이벤트로 앱 사이의 변경을 알릴 수 있음

EDA 자체가 외부 브로커나 비동기 처리를 필수로 만들지는 않습니다. 내부 디스패처가 같은 호출 스택에서 핸들러를 동기 실행할 수도 있습니다. 이후 본문은 브로커를 사용하는 비동기 분산 구성을 중심으로 설명합니다.

브라우저의 cart.changed와 서버의 내구성 있는 이벤트 전달은 서로 다른 실행 환경입니다. UI 이벤트 버스에 서버 브로커의 보관·재시도·전달 보장이 자동으로 생기지는 않습니다.

내부 이벤트는 트랜잭션과 어떤 관계가 있나요?

같은 프로세스여도 핸들러의 실행 시점과 트랜잭션 참여 여부를 정해야 합니다. 커밋 전에 외부 메일을 보내면 DB 롤백으로 그 메일을 회수할 수 없습니다. 커밋 후 메모리에서만 전달하면 프로세스 종료로 이벤트를 놓칠 수 있습니다.

도메인 내부의 사실을 표현하는 내부 이벤트와 외부 소비자를 위한 통합 이벤트는 공개 범위와 계약이 다를 수 있습니다. 외부 전달이 중요하면 Outbox처럼 DB 커밋과 발행할 기록을 연결하는 방식을 검토합니다.

PUBLISH · SUBSCRIBE

독립 구독과 같은 구독 안의 작업 분담을 구별합니다.

Publish/Subscribe에서는 관심 있는 소비자들이 독립 구독으로 같은 사실에 반응합니다. 반면 Competing Consumers는 같은 구독의 작업을 여러 실행 인스턴스가 분담하는 방식입니다. 배송 처리기를 늘린다고 모든 처리기가 같은 주문의 출고를 각각 수행해야 하는 것은 아닙니다.

독립 구독은 제품에 따라 별도 큐, 구독 또는 소비자 그룹 등으로 구현합니다. 메시지를 전달받는 단위와 순서·병렬 처리·보관의 단위는 사용하는 브로커의 모델에 맞춰 확인합니다. 브로커 이름만으로 원하는 의미가 보장되지는 않습니다.

비동기 전달의 시간

발행 성공을 전체 업무 완료로 해석하지 않습니다.

발행자의 요청 응답을 어디까지 기다릴지는 제품 계약입니다. 주문 확정만 끝났다면 “주문 확정 · 배송 준비 대기”처럼 현재 사실을 보여 줄 수 있습니다. 여러 소비자의 완료가 필요하면 결과 이벤트나 조회 모델로 진행 상태를 따로 관리합니다.

Eventual Consistency · 최종적 일관성
주문·배송·집계의 반영 시점이 다를 수 있습니다. 필요한 이벤트가 처리되고 실패가 복구되면 각 상태가 설계한 업무 규칙에 맞게 따라가도록 합니다.

최종적 일관성이 “기다리면 어떤 실패든 저절로 해결된다”는 뜻은 아닙니다. 누락·장기 실패를 찾고 복구하는 절차, 지연의 허용 범위와 사용자가 볼 상태를 정해야 합니다.

TRANSACTIONAL OUTBOX

업무 변경과 발행할 기록을 같은 트랜잭션에 남깁니다.

DB 저장과 브로커 발행을 각각 실행하면 둘 중 하나만 성공할 수 있습니다. 저장 후 발행에 실패하면 후속 업무가 시작되지 않고, 커밋 전에 발행하면 나중에 롤백될 상태가 외부에 알려질 수 있습니다.

Outbox는 업무 데이터와 발행할 이벤트 기록을 같은 로컬 트랜잭션으로 저장합니다. 전달기는 커밋된 기록을 읽어 발행하고, 실패하면 재시도합니다. 폴링이나 변경 데이터 캡처(CDC) 등을 사용할 수 있습니다.

Outbox를 쓰면 이벤트가 정확히 한 번만 발행되나요?

아닙니다. 브로커가 이벤트를 받았지만 전달기가 완료 표시 전에 중단되면 같은 이벤트를 다시 발행할 수 있습니다. 이벤트 ID를 유지하고 소비자가 중복 효과를 막도록 설계합니다.

Outbox에도 운영이 필요합니다. 전달기 중단, 오래된 미발행 기록, 정리 정책과 재시도 상태를 관측해야 합니다. 업무 데이터와 Outbox가 실제로 같은 트랜잭션에 참여하는지도 확인합니다.

중복 · 순서 · 실패

전달 보장과 업무 효과의 보장을 나눠 설계합니다.

At-least-once 전달에서는 재전달을 전제로 소비자의 멱등성(Idempotency)을 설계합니다. 중복 확인과 업무 변경을 분리하면 그 사이의 장애나 동시 실행으로 중복 효과가 생길 수 있습니다. 소비자·처리 종류별 이벤트 ID에 고유 제약을 두고 업무 변경과 원자적으로 확정하는 식으로 제어합니다.

상황설계할 대응주의할 점
일시 장애횟수·간격·백오프를 정한 재시도무한 즉시 재시도는 부하와 장애를 키울 수 있음
계속 실패하는 메시지격리·실패 대기열(DLQ), 알림과 복구 절차DLQ로 이동한 사실만으로 업무가 완료되지는 않음
중복 전달소비자별 처리 ID, 업무 제약, 멱등 키소비자 DB 밖의 효과는 같은 로컬 트랜잭션에 자동 포함되지 않음
순서 역전업무 식별자 기반 분할·직렬 처리, 상태 버전 검사 등전체 이벤트의 전역 순서와 단일 주문의 처리 순서는 다름
소비가 생산을 따라가지 못함적체·지연 관측, 병렬도·처리량·유입 조절처리기를 늘려도 같은 키의 순서 제약이나 DB 병목이 남을 수 있음
재처리·리플레이원래 이벤트 ID와 의미 유지, 재실행 정책통계 재계산과 결제·메일 재실행의 위험은 다름
At-most-once·At-least-once·Exactly-once는 어떻게 읽나요?

At-most-once는 정의한 범위에서 최대 한 번 전달·처리하는 보장이며 누락 가능성을 감수할 수 있습니다. At-least-once는 보장 범위와 전제 아래 재전달로 누락을 줄이는 대신 중복을 허용합니다. 보관 만료·영구 장애·잘못된 확인 처리까지 무조건 해결한다는 뜻은 아닙니다.

Exactly-once라고 표현된 기능은 보장 경계를 확인해야 합니다. 특정 브로커·스트림 처리·트랜잭션 범위의 보장을 외부 결제나 메일까지 포함한 전체 업무 효과의 보장으로 확대하면 안 됩니다. 소비자 DB와 외부 시스템 각각의 멱등·확정 방식을 검토합니다.

순서는 한 줄의 설정으로 끝나지 않습니다. 같은 키의 전달 순서를 보장해도 소비자의 병렬 실행이나 재시도에서 적용 순서가 달라질 수 있습니다. 상태 전이 규칙과 버전 검사를 함께 설계합니다.

이벤트 계약과 데이터

이벤트를 오래 이해할 수 있도록 의미와 버전을 관리합니다.

이벤트에는 누가 어떤 사실을 언제 발행했는지와 소비자가 필요한 데이터를 담습니다. 다음은 설명용 메시지입니다. 특정 브로커나 CloudEvents 표준 형식을 그대로 구현한 예시는 아닙니다.

{
  "eventId": "evt-17",
  "type": "OrderConfirmed",
  "schemaVersion": 1,
  "source": "orders",
  "occurredAt": "2026-11-18T01:00:00Z",
  "subject": "order-2048",
  "aggregateVersion": 7,
  "correlationId": "checkout-315",
  "data": {
    "orderId": "order-2048",
    "total": { "amount": "42000", "currency": "KRW" }
  }
}
계약 항목역할설계 시 확인
eventId동일한 사실의 발행·재전달을 식별이벤트마다 안정된 ID, 소비자별 중복 기록 범위·수명
type · source사실의 의미와 발행 책임을 표현어떤 업무 조건에서 발행하는지와 소유 팀
schemaVersion메시지 데이터 형식의 버전추가·삭제·의미 변경과 구버전 소비자의 호환성
subject · aggregateVersion대상 업무와 그 상태의 버전을 식별이벤트 스키마 버전과 업무 상태 버전은 별개
occurredAt발생 시각을 전달시계 오차가 있으므로 전체 처리 순서의 유일한 기준으로 쓰지 않음
correlationId하나의 사용자 요청·업무 흐름을 연결이벤트 ID·주문 ID·분산 추적 정보와 구분해 관리
data소비자가 반응할 때 필요한 정보최소 공개 범위, 개인정보·보관 기간, 원본 상태와의 관계
식별자만 보내나요, 필요한 데이터도 함께 보내나요?

변경 알림(Event Notification) 방식은 식별자 등 작은 메시지를 보내고 소비자가 상세 정보를 조회하도록 할 수 있습니다. 메시지는 작지만 조회 API의 가용성에 의존하며, 조회 시점의 최신 상태가 이벤트 발생 당시와 다를 수 있습니다.

상태를 실어 보내는 방식(Event-Carried State Transfer)은 소비자가 필요한 데이터를 이벤트에 담아 후속 조회를 줄일 수 있습니다. 대신 데이터 중복, 스키마 호환성과 개인정보·보관 정책을 더 관리해야 합니다. 앱의 내부 Entity나 DB 행 전체를 그대로 공개할 필요는 없습니다.

여러 단계의 업무 조정

이벤트 협력과 전체 업무의 진행 책임을 함께 설계합니다.

관점작동 방식필요한 관리
Choreography · 참여자 반응각 참여자가 이벤트에 반응하고 필요한 결과 이벤트를 발행전체 흐름을 추적할 이벤트 계약·소유자·실패 처리
Orchestration · 조정자 진행조정자가 진행 상태를 갖고 참여자에게 작업을 요청하며 결과를 해석조정 상태의 영속화·재시도·시간 초과·중복 제어
Saga · 분산 업무의 단계와 보상참여자의 로컬 트랜잭션들을 연결하고 실패 시 업무상 보상을 수행각 단계의 성공·실패·결과 불명 상태와 보상 가능 범위

Choreography와 Orchestration은 업무를 조정하는 관점이며 EDA와 함께 설계할 수 있습니다. 조정자가 명령을 보내고 참여자가 결과 이벤트를 발행하는 조합도 가능합니다. Saga는 두 조정 방식 모두로 구현할 수 있습니다.

이벤트를 사용해도 여러 서비스의 DB 변경이 하나의 ACID 트랜잭션이 되지는 않습니다. 보상은 과거를 지우는 전역 롤백이 아니라 취소·환불 같은 새로운 업무입니다. 결제 시간 초과처럼 결과가 불명확한 경우에는 확인·조정 절차도 필요합니다.

모든 후속 작업이 핵심 업무의 성공 조건인 것은 아닙니다. 주문 확정에 반드시 필요한 재고·결제와, 나중에 완료해도 되는 통계·안내를 구별해 완료 기준과 실패 정책을 정합니다.

EVENT SOURCING · CQRS

이벤트를 쓴다는 사실만으로 저장 방식까지 결정되지는 않습니다.

일반적인 DB에 현재 주문 상태를 저장하고 Outbox로 이벤트를 발행하는 시스템도 EDA입니다. 브로커의 이벤트 보관이나 재생 기능만으로 Event Sourcing의 완전한 원본 이력·재구성 계약이 자동으로 생기지는 않습니다.

HTTP API와 이벤트도 함께 사용합니다. 즉시 응답이 필요한 조회나 명령에는 요청·응답을 사용하고, 발생한 사실의 전파와 후속 작업에는 이벤트를 사용할 수 있습니다. 어떤 상호작용에 어떤 완료 기준이 필요한지부터 결정합니다.

하나의 사실에 여러 기능이 독립 반응하거나, 업무별 처리 속도가 다르거나, 후속 처리를 분리해야 할 때 EDA가 도움이 됩니다. 반면 즉시·원자적으로 끝나야 하는 작은 로컬 업무는 직접 호출과 DB 트랜잭션으로 단순하게 유지할 수 있습니다.

이 구성을 다시 읽어 보기

Microservices를 써야 EDA를 적용할 수 있나요?

아닙니다. Monolith나 Modular Monolith 안에서도 이벤트 디스패처로 업무 모듈을 연결할 수 있습니다. 분산 EDA에서는 네트워크·저장·재전달 문제를 추가로 다룹니다.

브로커가 수락했으면 사용자에게 모든 일이 끝났다고 해도 되나요?

브로커 수락과 각 소비자의 업무 완료는 다릅니다. 제품이 약속한 완료 조건을 만족했는지 따로 판단하고, 진행 중 상태와 후속 실패를 표현합니다.

Outbox와 멱등 소비자를 함께 설명하는 이유는 무엇인가요?

Outbox는 DB 변경과 발행 의도를 함께 남겨 누락 위험을 줄입니다. 그 전달 과정과 소비 확인에서는 중복이 생길 수 있으므로 소비자가 중복 업무 효과를 막는 설계도 필요합니다.

EDA를 쓰면 구성 요소 사이의 의존성이 없어지나요?

직접 호출 대상과 실행 시점에 대한 의존성을 줄일 수 있습니다. 이벤트 의미·스키마·가용성·진행 상태에 대한 의존성은 남으므로 이를 명시적으로 관리합니다.
