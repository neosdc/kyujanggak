CQRS
상태를 바꾸는 모델과 읽는 모델을 나눕니다.

명령(Command)은 업무 의도를 실행하고, 조회(Query)는 필요한 정보를 반환합니다. 두 책임과 모델을 분리해 각 목적에 맞게 설계하는 패턴입니다.

COMMAND QUERY RESPONSIBILITY SEGREGATION

명령은 의도를 실행하고, 조회는 필요한 정보를 돌려줍니다.

CQRS는 Command Query Responsibility Segregation의 약자입니다. 주문의 유효성을 지키는 변경 모델과, 주문 목록·상세를 읽기 좋은 형태로 제공하는 조회 모델을 각 목적에 맞춰 설계합니다. 두 모델은 같은 업무 사실을 다른 형태로 표현할 수 있습니다.

구분Command · 명령Query · 조회
목적상태를 바꾸는 업무 의도를 실행현재 알고 있는 정보를 읽기 좋은 형태로 반환
예PlaceOrder, CancelOrderGetOrderDetail, ListCustomerOrders
중심 책임권한·업무 규칙·불변식·동시성조회 권한·필터·정렬·페이지·표현에 맞는 구조
모델 예행동과 규칙을 가진 Order AggregateOrderListItem, OrderDetailView 같은 읽기 모델
저장 접근유효성을 지키며 변경·트랜잭션 수행전용 SQL·Join·View·Projection 등으로 필요한 값 조회
분리의 기준

핵심은 변경과 조회에 맞는 모델·책임입니다. HTTP의 GET·POST를 나누거나 Handler 클래스를 추가하는 것만으로 CQRS의 설계 목적이 완성되지는 않습니다.

CQS와 CQRS는 어떻게 다른가요?

CQS(Command–Query Separation)는 한 연산을 상태를 바꾸는 Command와 값을 돌려주는 Query로 구분하는 원칙입니다. CQRS는 이를 시스템의 변경·조회 모델과 책임의 분리로 확장해 설명합니다.

실무 CQRS의 Command는 처리 결과·새 ID·버전·오류를 반환할 수 있습니다. 엄격한 CQS의 “명령은 값을 반환하지 않는다”를 모든 API 응답에 그대로 강제할 필요는 없습니다. Query도 로깅·메트릭 같은 부수 기록을 할 수 있으나, 업무 상태를 바꾸는 작업을 숨겨 넣지 않도록 합니다.

같은 주문을 두 목적에 맞게 표현

쓰기 모델의 불변식과 읽기 모델의 형태를 따로 최적화합니다.

업무 요구명령 쪽 설계조회 쪽 설계
주문 생성Order.place가 수량·금액·상태의 유효성 검사생성된 주문 ID·접수 상태를 화면에 표시
주문 취소현재 상태·소유자·동시 변경을 확인하고 취소목록에서 상태·취소 가능 표시를 제공
고객 주문 목록목록 화면에 맞추려고 Aggregate를 확장하지 않음주문 번호·고객 표시명·총액·상태를 평평한 DTO로 반환
매출 통계통계 화면과 별개로 주문의 변경 의미를 유지집계 테이블·분석 쿼리 등 읽기에 맞는 구조 사용

읽기 모델이 화면에 취소 가능을 표시하더라도, 실제 취소 명령은 최신의 권위 있는 상태로 규칙을 다시 확인합니다. 조회 결과를 본 뒤 다른 요청이 상태를 바꿀 수 있기 때문입니다. 재고·잔액 판단도 지연된 Projection만 믿고 확정하지 않습니다.

조회가 쓰기 Aggregate를 꼭 거쳐야 하나요?

반드시 그렇지는 않습니다. 조회 경로가 전용 SQL이나 읽기 모델을 사용해 필요한 결과를 직접 만들 수 있습니다. 이때 조회 권한·민감 정보 필터·테넌트 경계를 동일하게 지켜야 합니다.

풍부한 도메인 모델은 복잡한 명령에 유용하지만 CQRS가 항상 DDD나 Aggregate를 요구하지는 않습니다. 이 문서의 Order는 업무 규칙의 차이를 보여 주는 예시입니다.

저장소 분리는 선택

같은 DB로 시작할 수도 있고, 별도 Projection을 둘 수도 있습니다.

구성얻는 점추가로 설계할 점
같은 앱 + 같은 DB쓰기 모델과 전용 조회를 단순하게 분리접근 권한·쿼리·모델 경계, 실제 읽기 일관성
같은 DB 안의 별도 읽기 테이블읽기 스키마 최적화, 필요하면 같은 트랜잭션으로 갱신두 표현의 갱신 책임과 저장·쓰기 비용
별도 Read Store + 비동기 Projection조회 부하·스키마·저장 기술을 독립 최적화전달 신뢰성·중복·순서·지연·재구축
별도 프로세스·서비스읽기와 변경의 실행 자원·배포를 분리 가능네트워크·운영·버전 호환·보안 경계

Eventual Consistency는 CQRS의 필수 속성이 아닙니다. 비동기 Projection이나 복제본을 사용하면 최신 쓰기가 조회에 늦게 보일 수 있습니다. 같은 DB라도 캐시·읽기 복제본·트랜잭션 격리에 따라 관측 결과가 달라지므로 실제 읽기 경로를 확인합니다.

Projection은 무엇인가요?

원천 데이터의 변경을 읽기 목적에 맞는 표현으로 반영한 모델입니다. 예를 들어 주문 이벤트를 받아 고객별 주문 목록의 상태·총액을 갱신합니다. CQRS의 읽기 모델은 꼭 이벤트 기반으로 미리 만들어야 하는 것은 아니며, 같은 DB의 전용 쿼리로 만들 수도 있습니다.

쓰기 성공과 조회 반영 사이

사용자가 보게 되는 지연을 응답 계약과 화면 흐름에 반영합니다.

필요한 사용자 경험가능한 방법주의점
클릭 직후 확정 결과 표시명령 응답의 처리 결과·ID·버전을 사용요청 접수와 DB 커밋을 구분해 응답 계약 명시
목록의 최신 반영 확인필요 버전까지 Polling·구독·제한된 대기타임아웃·실패·지연 상태를 화면에 표현
처리 중에도 응답비동기 접수 ID와 상태 조회 제공접수 성공은 업무 성공과 다름 · 거절·재시도 경로 필요
중요한 업무 결정권위 있는 쓰기 모델에서 다시 판단지연된 읽기 모델만으로 재고·잔액·권한을 확정하지 않음

UI는 성공 직후 결과를 일시 반영할 수 있지만, 서버의 확정 상태와 나중에 조정하는 정책이 필요합니다. “언젠가 맞는다”는 표현에는 전달·재시도·장애 복구가 정상화된다는 조건이 포함됩니다.

CQRS · EDA · EVENT SOURCING

함께 쓸 수 있지만, 각각 다른 질문에 답합니다.

개념답하는 질문필수로 따라오지 않는 것
CQRS상태 변경과 조회의 모델·책임을 어떻게 나누는가?별도 DB·메시지 브로커·비동기·Event Sourcing
EDA구성 요소가 어떤 이벤트로 반응·협력하는가?명령·조회 모델의 분리·이벤트 이력을 상태 원천으로 저장
Event Sourcing상태를 어떤 기록에서 복원하는가?CQRS나 별도 조회 저장소를 반드시 사용해야 한다는 조건
조회 모델은 언제든 이벤트를 재생하면 복구되나요?

복구에 필요한 원천 데이터와 변환 규칙이 남아 있어야 합니다. 일반 Outbox는 전송 후 삭제될 수 있고, 현재 상태 DB는 과거의 모든 변화를 보존하지 않을 수 있습니다. 둘을 완전한 Event Store라고 가정하면 안 됩니다.

현재 상태로 충분한 읽기 모델은 Snapshot·전체 추출과 이후 변경을 연결해 재구축할 수 있습니다. 이벤트 기반 재생은 보존 이력, 이벤트 스키마 버전, 처리 로직 호환, 중복·순서, 재생 중 외부 부작용 억제를 함께 설계합니다.

실패·중복·순서·보안

두 모델을 운영하려면 변경 전달도 제품 기능처럼 관리합니다.

문제필요한 정책주문 예시
명령 중복 실행요청 ID·멱등 키와 원자적인 중복 처리응답 유실 뒤 같은 생성 요청이 와도 주문을 중복 생성하지 않음
쓰기 동시성버전 검사·잠금·조건부 갱신 등배송과 취소가 경쟁할 때 허용된 상태 전이만 확정
이벤트 유실·중복Outbox·전달 재시도·멱등 ConsumerDB 갱신과 처리 기록을 필요한 원자성 범위에서 관리
역순·버전 누락주문별 순서·버전·Gap 감지·재동기화최신 취소 상태가 늦게 온 생성 이벤트로 되돌아가지 않게 함
조회 지연·장애처리 지연·대기량·실패·재처리 상태 관측최신 반영 버전과 사용자 대기 시간을 확인
조회 보안읽기 경로별 권한·필드·테넌트 필터빠른 조회 SQL이 다른 고객 주문을 노출하지 않도록 검사

모든 이벤트에 대한 전역 순서를 요구하기보다 업무에 필요한 순서 범위를 정합니다. 주문별 버전이 유용할 수 있으며, 단순히 오래된 버전을 무시해도 되는지는 Projection이 전체 상태 갱신인지 증분 계산인지에 따라 다릅니다.

주문 ID·명령 ID·이벤트 ID와 Trace Context를 연결하면 지연·실패를 추적하기 쉽습니다. OpenTelemetry와 Jaeger는 이 실행 경로를 관측하는 도구이며, 정합성을 보장하는 전달 장치는 아닙니다.

배포 방식·내부 구조와의 관계

모놀리스의 한 업무 영역에도 CQRS를 적용할 수 있습니다.

기존 개념함께 적용하는 방법주문 예시
Monolith / Modular Monolith한 배포 단위 안에서 모델·Handler를 분리주문은 CQRS, 상품 관리 화면은 단순 CRUD로 유지 가능
Microservices한 서비스 내부 또는 분리된 읽기·쓰기 실행 구성CQRS를 이유로 두 개 서비스를 반드시 만들 필요 없음
Hexagonal / Onion / Clean명령·조회 계약과 Adapter를 의존성 규칙에 맞춰 배치쓰기 Use Case는 Domain 규칙, 조회는 전용 Query Port·Adapter 사용
MVC / SPA + APIUI가 업무 의도를 Command로 보내고 Query 결과를 표시REST·GraphQL 등 전송 방식 자체가 CQRS를 결정하지 않음
EDA선택적으로 이벤트로 읽기 모델 갱신저장과 발행·소비의 일관성·재시도는 별도 설계

Modular Monolith · Microservices · EDA

적용 판단

변경 규칙이 복잡하거나 조회 형태·부하가 크게 다를 때 검토합니다. 단순 CRUD에 복잡성을 더하기 전에, 같은 DB의 전용 조회만으로 요구를 만족하는지 확인합니다.

적용 순서는 어떻게 잡을 수 있나요?

한 업무 영역에서 명령의 의도와 조회 결과 모델을 명확히 나눕니다. 같은 프로세스·DB에서 효과를 확인하고, 지연·용량·보안 요구가 뚜렷할 때 별도 Projection과 실행 자원을 검토할 수 있습니다. 모든 영역을 같은 방식으로 바꿀 필요는 없습니다.
