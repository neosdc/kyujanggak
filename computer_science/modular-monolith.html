SOFTWARE ARCHITECTURE · MODULAR MONOLITH

Modular Monolith
경계가 있는 모듈, 하나의 애플리케이션

업무 기능을 책임과 데이터 소유권이 분명한 모듈로 나누고, 모듈끼리는 공개 인터페이스로 협력합니다. 애플리케이션은 함께 배포합니다.

정의와 적용 범위

업무 경계를 유지하면서 Monolith의 배포 방식을 사용합니다.

구성 원칙의미주문·재고 예시
업무별 모듈같은 업무 규칙과 변경 이유를 가진 기능을 한 경계에 모음주문 생성·취소는 주문, 재고 예약·해제는 재고가 담당
명시적인 계약다른 모듈이 사용할 기능과 데이터 형식을 공개InventoryApi.reserve()와 예약 결과 객체
내부 구현 은닉다른 모듈이 내부 클래스·테이블 구조에 직접 의존하지 않게 관리재고 Entity·Repository·수량 갱신 SQL은 재고 내부
하나의 애플리케이션모듈이 같은 애플리케이션의 실행·릴리스 단위에 포함됨주문·재고·회원을 하나의 API 애플리케이션으로 배포

이 문서는 주문·재고 관리 서비스의 백엔드 애플리케이션을 예로 듭니다. 앞에 SPA를 두고 뒤에 DB를 두는 구성에도 적용할 수 있습니다. Modular Monolith는 애플리케이션 내부의 모듈 구조를 설명하므로, 특정 Tier 수나 MVC·SPA 같은 화면 구현 방식을 강제하지 않습니다.

모듈의 경계는 폴더 이름보다 의존성 규칙에서 드러납니다.
주문 코드가 재고의 내부 클래스와 테이블을 마음대로 사용한다면, 디렉터리가 나뉘어 있어도 경계를 유지하기 어렵습니다.

공개 계약과 내부 구현

다른 모듈에는 필요한 기능만 공개합니다.

주문 모듈은 ‘상품을 이 수량만큼 예약한다’는 업무 의도를 전달합니다. 재고 모듈은 가용 수량 계산, 동시성 처리와 저장 방식을 책임지고 예약 결과를 반환합니다. 호출자는 재고 테이블이나 ORM Entity를 알 필요가 줄어듭니다.

계약에 드러낼 것

  • 예약·해제처럼 의미가 분명한 작업
  • 입력과 결과의 데이터 형식
  • 실패 조건과 예외·오류 처리 규칙
  • 트랜잭션 참여와 호출 시점의 약속

모듈 내부에 둘 것

  • 도메인 객체의 내부 상태와 변경 방법
  • 테이블·Entity·Repository의 세부 구조
  • 계산 알고리즘과 SQL 구현
  • 외부에 필요 없는 보조 클래스
코드는 어떤 식으로 묶을 수 있나요?
modules/
  orders/
    api/                 공개 계약
    internal/
      application/       주문 유스케이스
      domain/            주문 상태·규칙
      persistence/       주문 데이터 접근
  inventory/
    api/                 InventoryApi·예약 결과
    internal/
      application/
      domain/
      persistence/

업무별 모듈 안에서 application·domain·persistence 같은 Layer를 나눌 수 있습니다. 이 디렉터리 이름은 예시이며, 실제 경계는 접근 제한자·빌드 모듈·의존성 검사 등으로 유지해야 합니다.

의존 방향

여러 모듈이 같은 업무 규칙을 사용할 수 있습니다.

주문은 재고 예약을, 반품은 재고 복원을 요청할 수 있습니다. 각 호출자가 재고 규칙을 따로 구현하기보다 재고 모듈의 계약을 사용합니다. 이때 재고가 주문·반품의 내부 구현을 다시 참조하지 않도록 의존 방향을 관리합니다.

기능을 추가할 때마다 서로를 참조하는 순환 의존성이 생기면 모듈을 따로 이해하고 검증하기 어려워집니다. 계약의 위치, 업무 조정 책임과 이벤트 구독 방향을 검토합니다. 인터페이스나 이벤트를 도입했다고 의존성 문제가 자동으로 사라지지는 않습니다.

업무 모듈은 무엇을 기준으로 나누나요?

주문, 재고, 회원처럼 업무 능력과 규칙의 소유권을 기준으로 시작할 수 있습니다. 함께 바뀌는 데이터와 규칙, 사용하는 업무 용어, 실패했을 때 책임질 모듈을 살펴봅니다. Controller·Service·Repository처럼 기술 역할만으로 전체 시스템을 나누면 각 업무 변경이 여러 경계를 가로지를 수 있습니다.

도메인 주도 설계의 Bounded Context는 경계를 찾는 데 도움을 줄 수 있습니다. 모든 모듈이 반드시 하나의 Bounded Context와 정확히 대응해야 하는 것은 아닙니다. 너무 잘게 나눠 호출과 계약이 과도해지면 경계를 다시 조정할 수 있습니다.

데이터 소유권

DB를 함께 써도, 각 데이터의 주인은 구분합니다.

재고 수량 변경은 재고 모듈의 공개 작업을 통해 요청합니다. 주문 모듈이 재고 Repository를 직접 사용하거나 재고 테이블을 임의로 수정하면 재고의 규칙을 우회하기 쉽습니다. 데이터 소유권은 모듈의 책임을 코드와 저장소까지 이어 주는 원칙입니다.

하나의 DB를 쓴다고 모든 테이블을 자유롭게 공유하는 것은 아닙니다.
스키마를 나누는 것만으로 접근이 강제되는 것도 아닙니다. 코드 의존성과 SQL 접근 규칙을 함께 관리해야 합니다.

다른 모듈의 데이터가 필요한 조회·리포트는 어떻게 하나요?

공개 조회 인터페이스를 사용하거나, 여러 모듈의 결과를 조합하는 조회 유스케이스를 둘 수 있습니다. 조회량과 지연 요구가 크면 별도의 읽기 모델·뷰·프로젝션을 검토할 수 있습니다.

공유 DB의 조인이나 모듈 간 외래 키를 허용하는 정책도 가능하지만, 상대 모듈의 스키마와 변경 시점에 결합된다는 점을 명시해야 합니다. 허용 범위, 책임자와 변경 절차를 정해 예외가 암묵적인 의존성으로 퍼지지 않도록 합니다.

호출과 트랜잭션

공개 API를 통해 협력하면서 같은 트랜잭션에 참여할 수 있습니다.

외부로 공개하는 기능은 업무 단위로 정하고, 그 기능이 트랜잭션을 시작하는지 기존 트랜잭션에 참여하는지 계약을 분명히 합니다. 각 모듈이 별도로 커밋하거나 다른 연결·자원을 사용하면 같은 결과를 보장하지 못할 수 있습니다. 동시 수정에는 조건부 갱신·잠금 같은 별도의 제어도 필요합니다.

모듈 간 이벤트를 사용해도 되나요?

가능합니다. 주문 완료 이벤트를 알림 모듈이 구독하도록 만들 수 있습니다. 이벤트 역시 발행 시점, 전달 방식, 데이터 형식과 실패 처리가 있는 계약입니다. 같은 프로세스의 동기 이벤트 처리기는 호출자의 트랜잭션과 실패에 영향을 줄 수 있습니다.

커밋 후 처리할 작업이나 재시도가 필요한 작업은 그 요구를 따로 설계합니다. DB 커밋과 내구성 있는 이벤트 발행을 함께 보장해야 한다면 Outbox 같은 방식을 검토할 수 있습니다. 모든 모듈 호출에 메시지 브로커나 비동기 이벤트가 필요한 것은 아닙니다. 외부 결제 같은 작업도 로컬 DB 트랜잭션에 자동으로 묶이지 않습니다.

빌드와 실행

모듈별 책임이 있어도 배포와 프로세스 자원은 함께 관리합니다.

각 모듈을 따로 단위 테스트하거나 공개 계약을 중심으로 검증할 수 있습니다. 릴리스 전에는 모듈 간 호출과 DB 변경을 포함한 통합 검증도 필요합니다. 하나의 모듈을 고쳐도 일반적으로 전체 애플리케이션을 새 버전으로 배포합니다.

애플리케이션을 여러 인스턴스로 복제해 확장할 수는 있지만, 각 인스턴스에는 보통 전체 모듈이 포함됩니다. 같은 프로세스의 메모리·스레드·연결 자원을 공유하므로 모듈 경계가 프로세스 수준의 장애 격리를 제공하지는 않습니다.

경계를 유지하는 방법

규칙을 문서와 코드 검증에 함께 둡니다.

유지할 경계적용 방법의 예확인할 내용
코드 접근접근 제한자, 패키지·어셈블리, 빌드 모듈과 공개 export다른 모듈이 internal 클래스를 직접 참조하는가?
의존 방향아키텍처 검사·린트·빌드 의존성 규칙순환 의존성이나 허용하지 않은 모듈 참조가 생기는가?
계약공개 인터페이스와 입력·결과 객체, 계약 검증내부 Entity·테이블 구조가 다른 모듈에 노출되는가?
데이터 접근스키마·테이블별 소유자와 SQL 접근 정책다른 모듈의 테이블을 직접 읽고 갱신하는가?
트랜잭션유스케이스 경계와 참여 정책, 실패·동시성 검증실패했을 때 일부 모듈의 변경만 남을 수 있는가?
공유 코드공용 영역에 들어갈 타입과 변경 책임 제한공용 모듈이 여러 업무 Entity를 모으는 장소가 되는가?

공용 유틸리티나 작은 공통 값 타입을 둘 수는 있습니다. 다만 여러 업무의 상태와 규칙을 모두 공용 영역으로 옮기면 모듈 경계가 다시 흐려질 수 있습니다. 언어·프레임워크가 허용하는 접근 제한과 자동 검증을 조합해 팀이 유지할 수 있는 수준으로 적용합니다.

장점과 비용은 무엇인가요?

장점: 업무 규칙의 위치와 변경 책임이 분명해지고, 내부 구현을 바꿀 때 다른 모듈의 영향을 줄일 수 있습니다. 프로세스 내부 호출과 단일 애플리케이션 운영 방식을 사용할 수 있습니다.

비용: 계약과 데이터 소유권을 설계하고 지키는 노력이 필요합니다. 모듈을 넘는 조회와 트랜잭션은 조정이 필요하고, 배포·자원·장애 영향은 여전히 애플리케이션 수준에서 함께 관리합니다. 모듈 경계는 나중에 조정할 수 있지만, 서비스 분리가 반드시 최종 목표일 필요는 없습니다.

이 구조를 다시 읽어 보기

폴더를 orders와 inventory로 나누면 Modular Monolith인가요?

폴더 분리는 시작점입니다. 공개 계약, 내부 구현 은닉, 데이터 소유권과 의존성 규칙이 실제 코드에서 유지되는지 함께 확인해야 합니다.

주문 모듈이 재고 수량을 바꿔야 하면 어떻게 하나요?

재고 모듈의 예약·해제 같은 공개 업무 작업을 호출합니다. 재고 규칙과 직접적인 데이터 변경은 재고 모듈이 책임집니다.

모듈을 따로 구현하고 검증하면 따로 배포할 수도 있나요?

이 문서의 구성에서는 모듈을 하나의 애플리케이션으로 함께 배포합니다. 모듈별 코드·검증 경계와 애플리케이션의 배포 경계를 구별합니다.
