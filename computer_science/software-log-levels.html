SOFTWARE LOGGING · DEVELOPMENT & OPERATIONS

Log Level은 사건의 심각도를,
출력 설정은 기록할 범위를 정한다

Software의 로그 레벨 상세 안내서. TRACE·DEBUG·INFO·WARN·ERROR·FATAL의 의미부터 로그 작성, 수집, 조회, 운영 정책까지 연결해서 이해한다.

대상: 개발자·System Engineer·SRE 및 소프트웨어 운영 참여자 · 2026.11.25 · 개념 설명과 교육용 예시

가장 먼저 구분할 것

logger.info(...)는 이 사건을 INFO로 분류한다. 설정의 level=INFO는 일반적인 최소 심각도 방식에서 INFO와 그보다 심각한 사건을 통과시킨다. 출력되지 않았다고 사건의 레벨이 바뀐 것은 아니다.

여섯 레벨 모두가 보편적인 표준은 아니다. Python 기본 logging에는 TRACE가 없고 CRITICAL이 있으며, Syslog에는 NOTICE·ALERT·EMERGENCY도 있다.[1]

그림과 표로 개요를 읽고 ‘더 보기’를 펼쳐 깊이 읽을 수 있다. 목차와 각주에는 대비를 높인 강조 스타일을 적용했다. 인쇄할 때는 상세 설명이 모두 펼쳐진다.

각 레벨의 의미

높은 레벨은 더 많은 정보가 아니라 더 심각한 사건을 뜻한다

위 표는 팀 정책을 만드는 출발점이다. 같은 이름도 라이브러리마다 정의가 다르며, Log4j의 문서는 표준 레벨을 제공하지만 어느 사건에 쓸지는 애플리케이션에서 정해야 한다고 설명한다.[2]

TRACE · 내부 실행 흐름을 재구성할 때

DEBUG보다 더 촘촘한 진행 정보를 담는 관행이다. 함수 진입·종료, 반복 상태, 프로토콜 처리 같은 정보가 필요할 때 쓸 수 있다. 모든 함수에 기계적으로 넣는 것이 목적은 아니다.

호출 빈도가 높은 구간에서는 적은 메시지 크기도 큰 부하가 된다. 필요한 모듈과 대상, 적용 기간을 한정한다. TRACE 로그와 분산 추적의 Trace는 이름이 비슷하지만 다른 개념이다. TRACE 메시지에 trace_id를 넣을 수 있고, INFO·ERROR 로그도 분산 추적에 연결할 수 있다.

DEBUG · “왜 이 경로를 선택했는가”를 남길 때

진단에 필요한 분기, 상태, 판단 근거를 남긴다. “처리 중” 대신 “캐시 엔트리가 만료되어 원본 조회를 선택했다”처럼 조사 질문에 답할 수 있어야 한다.

DEBUG라는 이유로 비밀번호나 토큰을 넣어도 되는 것은 아니다. 운영에서는 DEBUG가 꺼질 수 있으므로 필수적인 시작·완료·실패 기록을 모두 DEBUG에만 두지 않는다. 출력하지 않는 DEBUG 호출도 인수 계산 등 비용이 생길 수 있다.

INFO · 일상 운영에서 확인할 만한 정상 사건

INFO는 “중요하지 않음”이 아니라 “오류가 아닌 의미 있는 운영 사실”에 가깝다. 어떤 버전이 시작됐는지, 배치가 어떤 결과로 완료됐는지, 리더 역할이 바뀌었는지 같은 기록이다.

매 요청의 성공 기록이 필요한지는 트래픽과 목적에 따라 정한다. 고빈도 조회 성공을 전부 기록하기보다 접근 로그나 메트릭으로 다루는 편이 나을 수 있다. 반대로 중요한 상태 변경은 빈도가 낮아도 INFO 또는 별도 감사 사건으로 남길 가치가 있다.

WARN · 현재 결과와 미래 위험을 함께 기록할 때

대체 서버로 전환해 요청은 성공했지만 정상 경로가 고장났거나, 처리 여유가 줄어드는 상황에 적합할 수 있다. “무엇이 비정상인가, 현재 결과는 무엇인가, 언제 조치해야 하는가”를 함께 적는다.

모든 재시도·캐시 미스가 WARN은 아니다. 정상 설계에 포함된 흔한 동작이라면 DEBUG·메트릭으로 충분할 수 있다. 경고가 지속되면 언제 조사·알림·에스컬레이션할지 정해야 경고가 배경 소음으로 굳지 않는다.

ERROR · 실패한 작업의 범위를 명확히 할 때

ERROR는 보통 특정 요청이나 작업의 실패를 나타낸다. 프로세스 전체 종료를 뜻하지 않는다. 웹 서버가 다른 요청을 처리하고 있어도 주문 저장 한 건은 실패할 수 있다.

무슨 작업이 실패했는지, 어느 단계인지, 재시도와 보정이 가능한지, 외부에 어떤 결과를 반환했는지 적는다. 잘못된 결과나 데이터 유실처럼 예외 객체 없이 발생한 실패도 ERROR로 표현할 수 있다.

FATAL / CRITICAL · 계속할 수 없는 실행 범위를 밝힐 때

프로세스·애플리케이션 등 어떤 실행 단위가 더는 안전하게 동작하지 못하는지 명시한다. 워커 한 개의 종료와 전체 서비스 중단은 다르다. 플랫폼이 사용하는 이름과 심각도 정책을 따른다.

레벨 이름과 프로그램 제어 흐름은 분리해서 확인한다. Python의 critical()은 로그 호출이며 그 자체가 프로세스를 종료하지 않는다. 다른 API는 치명적 로그와 종료 동작을 묶기도 한다. 실제 사용 중인 API의 종료·flush·예외 동작을 확인한다.[3]

심한 충돌·강제 종료에서는 마지막 로그가 남지 않을 수 있다. 프로세스 종료 코드, 재시작 횟수, 코어 덤프, 런타임·호스트 이벤트 같은 별도 신호도 확인한다.

이벤트 레벨과 출력 임계값

INFO로 설정하면 일반적으로 INFO 이상을 통과시킨다

더 보기 · “INFO 이상”과 “로그를 더 자세히”의 방향

의미상 TRACE → DEBUG → INFO → WARN → ERROR → FATAL 순으로 더 심각하다. 최소 기준을 INFO에서 DEBUG로 낮추면 DEBUG까지 추가돼 더 자세해진다. 기준을 ERROR로 높이면 TRACE부터 WARN까지 제외돼 기록이 줄어든다.

“레벨을 올려 달라”는 요청은 모호하다. 심각도 기준을 높이자는 말인지, 자세한 로그를 늘리자는 말인지 구분해 “checkout 모듈의 최소 레벨을 DEBUG로 변경”처럼 쓴다. 숫자의 대소 비교 방향은 플랫폼마다 다르다.

더 보기 · 상속과 전파 때문에 예상과 다르게 나오는 이유

로거 이름이나 카테고리는 보통 계층을 이룬다. 해당 로거에 명시한 기준이 없으면 상위 설정에서 유효 레벨을 결정할 수 있다. 출력 대상에도 별도의 기준이 있을 수 있다.

Python에서는 자식 로거가 허용한 레코드가 조상 로거의 handler로 직접 전달될 때, 조상 로거 자체의 level·filter를 다시 적용하지 않는다. handler의 level·filter는 적용된다. 따라서 “부모 로거가 ERROR이니 자식의 DEBUG는 반드시 없어야 한다”는 추론이 틀릴 수 있다.[4]

이 세부 규칙을 다른 프레임워크에 그대로 적용하지 않는다. 유효 레벨, propagation/additivity, handler/appender/provider 설정을 해당 문서에서 확인한다.

현실적인 분류 기준

예외 유무보다 기대한 결과와 실패 범위를 먼저 본다

팀 정책에는 경계 사례를 포함한다. “WARN은 주의, ERROR는 오류”만 적으면 사람마다 판단이 달라진다. 어떤 작업 단위를 평가하는지, 정상적인 실패 응답은 무엇인지, 최종 결과를 어디서 기록하는지 함께 정한다.

더 보기 · HTTP 상태 코드와 로그 레벨을 일대일로 매핑하면 생기는 문제

모든 4xx를 WARN으로, 모든 5xx를 ERROR로 바꾸는 규칙만으로는 부족하다. 잘못된 비밀번호, 없는 리소스, 봇 스캔, 접근 제어 오작동이 같은 범주에 섞일 수 있다. 사용자 취소와 서버 내부 결함도 구분해야 한다.

접근 로그에는 상태 코드와 경로·지연·결과를 일관되게 기록하고, 애플리케이션 로그에는 진단 맥락을 남긴다. 공격 패턴은 개별 요청의 레벨과 별도로 집계·탐지한다. 응답이 성공이어도 잘못된 데이터나 미처리 작업이 생기면 업무적으로 실패일 수 있다.

“ERROR가 하나라도 나오면 즉시 호출”보다는 서비스별 오류율·업무 결과·지속성·탐지 목적을 정의한다. 데이터 손상이나 침해 징후처럼 단일 사건으로도 즉시 대응할 조건은 별도로 둔다. 로그를 바탕으로 만든 알림도 그 자체가 장애 등급을 확정하지 않는다.

더 보기 · 개발자·SE·SRE는 각각 무엇을 책임지는가?

개발자는 사건의 의미, 적절한 레벨, 구조화 필드, 예외 처리 경계와 민감정보 배제를 설계한다. SE·플랫폼 담당자는 실행 환경, 파일·표준 출력, 에이전트, 전달·저장·보관·권한과 자원 상태를 관리한다. SRE·서비스 운영자는 로그를 SLI·메트릭·추적과 연결하고 알림 품질과 대응 절차를 검토한다.

조직에 따라 한 사람이 여러 역할을 맡는다. 중요한 것은 사건 의미의 소유자, 파이프라인 운영자, 데이터 접근·보존 책임자가 명확하고 함께 품질을 개선하는 것이다.

좋은 로그의 구성

레벨만으로는 원인을 찾을 수 없고, 맥락을 연결해야 한다

“저장 실패”만으로는 어떤 서비스의 어떤 요청인지 알기 어렵다. 반대로 모든 객체를 문자열로 덤프하면 비용과 민감정보가 늘고 검색은 어려워진다. 조사 목적에 맞는 최소한의 구조화 필드를 정한다.

{
  "timestamp": "2026-11-25T14:02:10.123+09:00",
  "level": "ERROR",
  "event": "order_persist_failed",
  "message": "Order could not be persisted after retry exhaustion",
  "service": "checkout",
  "environment": "production",
  "version": "demo-build",
  "request_id": "req-demo-01",
  "trace_id": "0123456789abcdef0123456789abcdef",
  "span_id": "0123456789abcdef",
  "operation": "persist_order",
  "outcome": "failure",
  "retry_exhausted": true,
  "error_type": "TimeoutError"
}

가상 사건이며 필드 이름은 설명용 애플리케이션 스키마다. OpenTelemetry의 실제 전송 형식이나 특정 제품의 필수 스키마를 그대로 나타내지 않는다. 예외 stack과 식별자는 실제 정책에 따라 제한·정제해 추가한다.

필드 묶음왜 필요한가?설계 시 주의점
발생·관측 시각실제 사건 순서와 수집 지연을 구분.명확한 시간대와 형식. 호스트 시계 오차·재전송 때문에 순서가 뒤바뀔 수 있음.
level·event·message심각도, 사건 종류, 사람이 읽을 설명을 분리.event는 안정적으로 유지. ID와 자유 입력을 사건명에 섞지 않음.
service·environment·version어느 실행 환경과 변경에서 발생했는지 확인.운영·개발 환경 혼합 방지. 공통 메타데이터는 플랫폼이 주입할 수 있음.
request_id·trace_id·span_id여러 로그와 분산 호출을 연결.단순 요청 ID와 분산 추적 ID의 의미·형식을 구분. 신뢰 경계에서 외부 값 검증.
outcome·reason·error_type업무 거절과 시스템 실패, 원인 종류를 구분.같은 필드의 자료형을 유지. 예외 메시지의 민감정보·길이 제한.
더 보기 · 구조화 로그, JSON, 메시지 템플릿은 같은 뜻인가?

구조화 로그는 사건을 이름 있는 필드로 기록한다. JSON은 그 정보를 직렬화하는 형식 중 하나다. 메시지 문자열 안에만 JSON 비슷한 내용을 넣고 나머지 필드가 없으면 원하는 검색·집계가 어려울 수 있다.

메시지 템플릿은 고정된 문장과 변하는 값을 구분한다. 플랫폼에 따라 인수가 구조화 속성으로 보존되기도 하고, 최종 문자열로만 출력되기도 한다. “플레이스홀더를 썼으니 자동으로 JSON 필드가 생긴다”고 가정하지 않는다.

JSON은 직접 문자열 연결로 만들지 말고 올바른 직렬화기·인코더로 생성한다. 예외의 여러 줄 stack trace는 논리적으로 하나의 레코드로 연결하고, 수집기가 줄 단위로 쪼개거나 합치는 규칙을 확인한다.

더 보기 · OpenTelemetry의 SeverityText·SeverityNumber와 두 시각

OpenTelemetry 로그 데이터 모델은 원본 심각도 텍스트인 SeverityText와 정규화한 SeverityNumber를 구분한다. 원본 레벨을 보존하면 잘못된 숫자 매핑을 조사하기 쉽다.

Timestamp는 원본 시계로 측정한 사건 발생 시각, ObservedTimestamp는 수집 계층이 사건을 관측한 시각이다. 둘의 차이를 수집 지연의 단서로 볼 수 있지만 시계 오차도 고려해야 한다. Resource는 사건을 만든 실행 주체, Attributes는 개별 사건의 추가 속성을 담는다.[5]

TraceId·SpanId는 선택적 맥락이다. trace_id가 있어도 해당 추적 데이터가 샘플링·보관돼 있다는 보장은 없다. 반대로 로그가 없다고 추적 데이터도 없는 것은 아니다.

예외 처리와 로그 소유권

같은 실패를 계층마다 ERROR로 반복하면 실제 영향이 부풀려진다

예외는 처리 흐름의 정보다

예외는 기대한 입력 거절, 취소, 일시적 연결 실패, 프로그램 결함 등 여러 원인에서 발생한다. catch했다는 사실만으로 INFO도 ERROR도 결정되지 않는다.

실제로 복구했는지, 계속 처리하는 것이 안전한지, 최종 결과가 무엇인지 확인한다. ERROR를 없애려고 예외를 삼키면 실패는 남고 관측만 사라진다.

레벨과 stack trace는 별개다

ERROR여도 예외 객체가 없을 수 있고, DEBUG에 예외의 상세 맥락을 첨부할 수도 있다. 플랫폼에 맞게 원인 예외와 stack을 전달한다.

같은 stack을 반복 덤프하지 않도록 대표 사건을 남긴다. stack이나 예외 메시지에도 SQL·경로·인수·개인정보가 포함될 수 있다.

더 보기 · 재시도 중인 실패와 최종 실패를 구분하기

재시도 가능한 작업에서는 시도 attempt와 논리 작업 operation을 구분한다. 첫 시도의 타임아웃과 전체 주문 저장 실패는 다른 사건이다. 개별 시도는 DEBUG·WARN 등으로 정책화하고, 최종 성공·실패를 별도로 기록한다.

예상보다 긴 지연이나 반복적인 대체 경로 사용은 최종 성공이어도 경고할 수 있다. 반대로 드문 정상 재시도까지 모두 ERROR로 기록하면 서비스 실패율을 과장한다.

job_id·operation_id·attempt·retry_exhausted 같은 맥락을 사용할 수 있다. 실제 숫자와 의미는 스키마에 명시한다. 재시도 때문에 중복 실행될 수 있는 업무는 멱등성과 보정·재처리 절차도 함께 학습한다.

더 보기 · log-and-throw와 예외 체인

하위 계층에서 ERROR를 남기고 그대로 던진 뒤, 상위 계층도 같은 실패를 ERROR로 남기면 중복이 된다. 로그를 소유할 경계를 정하고 필요하면 하위 계층은 맥락만 보강해 원인 예외를 전달한다.

예외를 새 예외로 감쌀 때 원래 원인과 stack을 잃지 않게 한다. 다만 시스템 경계·라이브러리·비동기 작업처럼 추가 기록이 필요한 경우도 있다. 무조건 “한 번만 로그”보다 대표 실패와 독립적인 의미가 있는 사건을 구분하는 기준이 필요하다.

기록·수집·조회 경로

코드에서 호출했다고 저장·조회까지 성공한 것은 아니다

더 보기 · stdout·stderr, 파일 로그, 접근 로그의 차이

stdout·stderr는 출력 스트림이다. ERROR 레벨과 stderr는 동일 개념이 아니다. Python의 기본 StreamHandler는 stderr를 사용할 수 있고, 어떤 애플리케이션은 모든 레벨을 stdout에 JSON으로 보낸다. 수집기가 스트림만으로 심각도를 추정하면 잘못 분류할 수 있다.

파일 로그는 권한·경로·디스크·로테이션·수집 위치를 관리해야 한다. 컨테이너 내부 파일이 자동으로 중앙 수집되는 것은 아니다. 반대로 표준 출력도 런타임·에이전트 설정에 따라 누락될 수 있다.

접근 로그는 요청·응답·지연을 일관되게 기록하는 목적이고, 애플리케이션 로그는 내부 사건과 진단 맥락을 설명한다. 둘이 같은 요청을 기록해도 목적이 다르다. 요청 ID로 연결하고 중복 저장 비용을 검토한다.

더 보기 · 사건 순서, 중복 전송, 검색 결과의 빈틈

여러 호스트의 시계, 비동기 큐, 재시도와 배치 전송 때문에 조회 순서가 실제 발생 순서와 다를 수 있다. timestamp만으로 전역 인과관계를 단정하지 않고 trace·span·소스별 순서 정보를 함께 본다.

전송 재시도는 같은 사건을 중복 저장할 수 있다. 필요한 경우 이벤트 식별자와 중복 처리 정책을 정한다. 에이전트가 파일 교체·잘림을 추적하는 방식에 따라 로테이션에서 누락·재수집도 발생할 수 있다.

조회 결과가 없으면 “사건이 없었다”보다 “이 조건과 권한, 이 보존 범위에서 찾지 못했다”가 정확하다. 원본 시각과 수집 시각, 누락·드롭 지표를 함께 확인한다.

숫자와 이름의 차이

서로 다른 플랫폼의 숫자는 정규화 없이 비교하지 않는다

체계기본 이름·값비교와 주의점
Python loggingDEBUG 10 · INFO 20 · WARNING 30 · ERROR 40 · CRITICAL 50숫자가 클수록 심각. 기본 TRACE 없음. NOTSET 0은 일반 사건 레벨과 다르게 동작.
Apache Log4jTRACE 600 · DEBUG 500 · INFO 400 · WARN 300 · ERROR 200 · FATAL 100숫자가 작을수록 심각. OFF·ALL은 전체 비활성·활성 설정용 특수 값.

이 표는 각 체계의 값을 나란히 보여 준다. 행 사이의 레벨이 모두 정확히 일치한다는 매핑표는 아니다. 원본 이름·숫자·라이브러리와 버전을 보존하고, 수집 변환 규칙을 명시한다.[6]

더 보기 · OFF·ALL·NOTSET·None과 사용자 정의 레벨

OFF·ALL·None은 해당 플랫폼에서 출력을 비활성화하거나 모두 허용하는 설정에 쓰인다. 일반적인 사건을 “OFF 레벨로 기록”하는 것과 다르다. 이름이 없거나 다른 의미인 라이브러리도 있다.

Python NOTSET은 비루트 로거에서는 상위 로거의 유효 레벨을 찾게 한다. root와 handler에서는 동작 맥락이 다르므로 문서를 확인한다. “NOTSET은 INFO의 다른 이름”처럼 해석하지 않는다.

사용자 정의 레벨은 의미가 명확할 때만 도입한다. 대시보드·수집기·경보·외부 전송이 그 레벨을 모르면 잘못 분류하거나 누락할 수 있다. 보존 정책을 구분하려고 BUSINESS·AUDIT라는 새 심각도를 만들기보다 event_type·channel 같은 별도 필드를 검토한다.

더 보기 · Syslog의 Priority와 OpenTelemetry 매핑

Syslog의 PRI는 facility와 severity를 조합한 전송 헤더 값이다. RFC의 계산은 PRI = facility × 8 + severity다. 이 이름의 Priority는 장애 대응의 P0–P4와 다른 개념이다.[7]

OpenTelemetry는 원본 형식의 의미를 바탕으로 SeverityNumber에 매핑하도록 한다. 원본에 있는 Critical을 무조건 FATAL 범위에 넣는 등 이름만 본 변환은 피한다. 원본이 “더 심각한 오류”를 뜻하는지 “실행 지속 불가능”을 뜻하는지 확인하고 매핑 규약을 따른다.

SeverityText가 없거나 알 수 없는 레벨이 들어오면 기본값·보존 필드·파싱 실패 처리 규칙을 정한다. 미지정 심각도를 정상·INFO와 무조건 동일시하지 않는다.

운영 중 설정하기

자세한 로그는 필요한 범위와 시간에 한정해서 늘린다

  1. 조사 질문을 정한다. 어떤 경로·상태를 확인하면 원인 가설을 구분할 수 있는지 적는다.
  2. 적용 범위를 좁힌다. 특정 모듈·카테고리·배포 그룹에서 시작한다. 전역 DEBUG를 기본 선택으로 삼지 않는다.
  3. 정보 노출과 비용을 확인한다. 새로 출력되는 필드, 예상량, 저장·전송 여유를 검토한다.
  4. 변경을 추적한다. 담당자·이유·시작·만료·원복 방법과 실제 유효 설정을 기록한다.
  5. 경로 전체를 맞춘다. 소스만 DEBUG로 바꾸고 handler·수집기는 INFO로 두면 원하는 정보가 사라질 수 있다.
  6. 진단 후 원복·개선한다. 임시 로그가 아니라 지속적인 계측·메트릭·런북이 필요한지 판단한다.
더 보기 · 동적 레벨 변경, 환경 변수, 설정 우선순위

환경 변수나 설정 파일이 실제 레벨에 어떻게 반영되는지는 프로그램이 결정한다. 파일을 바꿔도 재시작 전에는 반영되지 않을 수 있고, 동적 변경이 다음 재시작에서 사라질 수 있다. 코드·설정 파일·환경·중앙 설정 중 무엇이 우선하는지 확인한다.

동적 변경 기능은 운영 권한과 변경 기록이 필요하다. 누가 무엇을 얼마나 오래 바꿨는지 추적하고 자동 만료를 검토한다. 외부에서 임의로 전역 DEBUG를 켤 수 있는 인터페이스는 정보·자원 노출을 늘릴 수 있다.

대상 사용자를 기준으로 진단 범위를 제한할 때도 개인정보와 권한을 고려한다. 사용자 입력이 직접 로그 설정이나 메시지 템플릿을 제어하지 않게 한다.

더 보기 · 레벨 변경으로 ERROR 수를 줄여도 실패가 해결되지는 않는다

잘못 분류한 정상 사건을 적절한 레벨로 고치는 것은 품질 개선이다. 반면 실제 실패를 INFO로 바꿔 대시보드를 조용하게 만드는 것은 관측을 왜곡한다.

레벨 정책이나 샘플링을 바꾸면 기존 알림·오류 추세가 달라질 수 있다. 변경 전후 수치가 같은 기준인지 표시하고, 실제 사용자 성공률과 독립적인 신호를 함께 검증한다.

성능과 비용

출력을 끈 로그도 비용이 생길 수 있고, 비동기도 무손실을 보장하지 않는다

호출 전 계산 비용

메시지 인수로 큰 객체를 직렬화하거나 데이터를 조회하면 레벨 필터 전에 실행될 수 있다. 문자열 포맷팅 지연과 인수 계산 지연은 다르다.

플랫폼의 매개변수 로깅·지연 평가 기능을 활용한다. 값 계산이 비싸면 enabled 검사를 고려하되, 로깅 인수에 업무상 부작용을 넣지 않는다.

출력 이후의 전체 비용

인코딩·잠금·파일 I/O·네트워크·수집·파싱·색인·검색·보관에 비용이 든다. 긴 stack이나 큰 JSON 하나가 여러 작은 로그보다 클 수 있다.

레벨 이름으로 로그량을 예측하지 않는다. 실제 사건 수와 직렬화 후 바이트, 출력 지연, 드롭·백프레셔를 측정한다.

더 보기 · 샘플링·레이트 제한·집계와 유실의 차이

샘플링은 정한 규칙으로 일부 사건을 선택한다. 레이트 제한은 일정 구간의 출력량을 제한한다. 집계는 반복 사건을 요약한다. 유실은 의도와 달리 사건이 사라지는 것이다. 화면에서 기록이 적다는 결과는 비슷해도 의미가 다르다.

반복 로그를 제한할 때는 억제된 사건 수와 대표 맥락을 남기는 방법을 검토한다. ERROR도 무제한 기록하면 시스템을 압박할 수 있지만, 감사·보안·복구에 필요한 사건을 무작정 샘플링해서도 안 된다.

필터·샘플링된 로그 건수를 그대로 서비스 오류율의 분자로 쓰면 편향될 수 있다. 메트릭을 주 계측으로 두거나, 샘플링 가중치·중복·분모를 정확히 처리한다. 로그와 분산 추적의 샘플링 정책은 독립적일 수 있다.

더 보기 · 로테이션·보존 기간·검색 가능 기간

로테이션은 파일 크기나 시간에 따라 현재 파일을 교체하는 동작이다. 보존 기간은 데이터를 얼마나 오래 유지할지, 검색 가능 기간은 어떤 저장 계층에서 즉시 조회할 수 있는지를 말한다.

파일을 회전시켰다고 보존 정책이 완성되는 것은 아니다. 오래된 파일 정리, 중앙 저장소의 삭제, 백업·복제본, 감사 보관과 법적 보존 요구를 함께 다룬다. 수집기가 회전된 파일을 따라가는 방식도 검증한다.

민감정보와 감사 기록

DEBUG도 비밀을 남기면 안 되며, INFO도 필수 감사 기록일 수 있다

관리할 내용구체적인 설계흔한 오해
비밀·민감정보 제외비밀번호, 토큰, 인증 헤더, 세션 값, 개인·금융정보 등은 목적에 맞게 제외·대체·마스킹.운영에서 DEBUG가 꺼져 있으니 민감정보를 넣어도 괜찮다.
출력 전 정제가능한 한 최초 기록 전에 허용 필드를 선별. 모든 출력 대상과 예외·URL·헤더를 점검.중앙 저장소에서 마스킹하니 로컬 파일과 전송 경로는 확인하지 않아도 된다.

감사 채널행위자·대상·행동·결과·시각·인가 맥락을 별도로 정의하고 필수 전달·보관을 설계.AUDIT는 항상 ERROR보다 높은 심각도여야 한다.

OWASP는 사건 속성의 일관성, 직접 기록하지 말아야 할 데이터, 로그 삽입 방지, 권한과 로깅 실패 검증을 함께 다룬다.[8] 로깅 보안은 레벨을 WARN으로 높이는 설정만으로 해결되지 않는다.

더 보기 · 마스킹·해싱·가명처리의 한계

항상 전체 객체를 기록한 뒤 특정 키만 지우는 방식은 새 필드와 중첩 구조를 놓칠 수 있다. 필요한 필드를 허용 목록으로 선택하고, 길이·형식·민감도를 검토하는 방법을 우선 고려한다.

이메일이나 사용자 ID를 해싱했다고 자동으로 익명 데이터가 되는 것은 아니다. 추측 가능성, 다른 데이터와의 연결, 보관·접근 목적에 따라 여전히 보호가 필요하다. 인증정보는 조사 편의만을 위해 해시해 보관하는 대상으로 삼지 않는다.

URL의 쿼리, 예외 메시지, stack trace, SQL·연결 문자열, 요청·응답 헤더에도 비밀이 섞일 수 있다. 구조화 출력과 매개변수 로깅은 비밀 제거를 대신하지 않는다.

더 보기 · 감사 로그와 일반 운영 로그의 전달 보장

일반 진단 로그는 일부 손실을 허용할 수 있지만, 특정 감사 기록은 완전성·무결성·보존이 필수일 수 있다. 운영 최소 레벨을 WARN으로 바꿨다는 이유로 INFO 수준의 감사 사건까지 사라지면 안 된다.

별도 채널·저장소·큐·재전송·일관성 요구를 정한다. 전달 실패 시 업무를 계속할지 제한할지는 해당 업무의 보안·규정·계약과 설계에 따른다. 이 문서가 모든 시스템에 단일 실패 정책을 정하지는 않는다.

로그가 업무 상태의 유일한 저장소가 되지 않도록 한다. 거래 원장이나 필수 업무 이벤트는 그 목적에 맞는 저장·전달 보장을 설계하고 운영 로그와 연결한다.

실행 예제와 팀 양식

레벨 정의를 코드와 운영 계약에 함께 반영한다

Python 예제: 로거는 DEBUG, 콘솔 출력은 INFO

독립된 Python 프로세스에서 실행할 수 있는 표준 라이브러리 예제다. 외부 서비스 호출 없이 가상의 타임아웃을 만든다. DEBUG는 로거에서 허용돼도 콘솔 handler에서 제외되며, critical() 이후에도 프로그램이 계속 실행된다.

import logging

log = logging.getLogger("demo.checkout")
log.setLevel(logging.DEBUG)
log.propagate = False

console = logging.StreamHandler()
console.setLevel(logging.INFO)
console.setFormatter(
    logging.Formatter("%(levelname)s %(name)s %(message)s")
)
log.addHandler(console)

log.debug("cache_path_selected path=%s", "origin")
log.info("batch_completed outcome=%s", "success")
log.warning("fallback_enabled dependency=%s", "cache")

try:
    raise TimeoutError("synthetic timeout")
except TimeoutError:
    log.exception("persist_failed request_id=%s", "req-demo-01")

log.critical("critical_demo reason=%s", "demonstration-only")
print("프로세스는 계속 실행됩니다.")

예제의 예외 메시지와 식별자는 가상 값이다. 운영 시스템의 구성과 handler를 초기화하는 배포 코드로 그대로 사용하지 않는다. 노트북이나 같은 인터프리터에서 설정 부분을 반복 실행하면 handler가 중복 추가될 수 있다.

실행 결과에서 확인할 점
  • DEBUG 메시지는 콘솔에 나오지 않는다. logger와 handler의 조건이 서로 다르기 때문이다.
  • INFO·WARNING·ERROR·CRITICAL은 출력된다. INFO 설정은 INFO 하나만 고르는 정확 일치 조건이 아니다.
  • exception()은 예외 처리 블록에서 ERROR 수준과 예외 정보를 함께 남긴다. 다른 수준이 필요하면 플랫폼의 exc_info 등 기능을 확인한다.
  • 마지막 “프로세스는 계속 실행됩니다.”도 출력된다. critical()을 호출했다는 사실만으로 프로그램이 종료되지 않는다.

기본 StreamHandler가 stderr를 사용하는 것과 로그의 level이 무엇인지는 별개다. 이 예제에서도 INFO가 stderr로 나올 수 있다.

더 보기 · 매개변수 로깅과 비싼 인수의 계산
log.debug("snapshot=%s", build_snapshot())

if log.isEnabledFor(logging.DEBUG):
    log.debug("snapshot=%s", build_snapshot())

위 코드는 개념 비교를 위한 조각이며 build_snapshot()의 구현은 생략했다. 첫 호출의 함수 인수는 debug() 호출 전에 계산된다. 문자열 포맷팅을 늦춰도 build_snapshot()이 자동으로 늦춰지는 것은 아니다.

enabled 검사는 비싼 계산을 건너뛰는 데 도움이 되지만 handler·수집기에서 나중에 제외될 수는 있다. 사용 중인 라이브러리가 supplier·lambda 같은 지연 인수 평가를 제공하는지도 확인한다. 업무에 필수적인 상태 변경을 이런 계산에 넣지 않는다.

혼동하기 쉬운 질문

로그가 보이는 방식과 소프트웨어의 실제 상태를 분리한다

레벨을 INFO에서 ERROR로 높이면 로그가 더 자세해지는가?

일반적인 최소 심각도 방식에서는 반대다. ERROR보다 덜 심각한 사건을 제외하므로 기록이 줄어든다. 더 자세히 보려면 DEBUG·TRACE 쪽으로 기준을 낮추되 범위와 기간을 한정한다.

WARN이 없고 ERROR가 없으면 정상인가?

아니다. 해당 코드가 실행되지 않았거나, 필터·수집·조회에서 사라졌거나, 문제 상황을 기록하는 코드 자체가 없을 수 있다. 외부에서 확인한 사용자 결과와 메트릭, 프로세스·수집 상태를 함께 본다.

ERROR는 반드시 예외가 발생했을 때만 쓰는가?

아니다. 결과 검증 실패, 처리 누락, 잘못된 응답처럼 예외 없이 실패할 수도 있다. 반대로 정상 제어 흐름에서 처리한 예외는 ERROR가 아닐 수 있다. 최종 작업 결과와 기대 동작으로 판단한다.

FATAL·CRITICAL을 기록하면 자동으로 종료되는가?

API에 따라 다르다. Python critical()은 종료를 일으키지 않는다. 종료를 포함하는 함수도 있으므로 해당 라이브러리의 설명을 확인한다. 로그 레벨, 실제 종료, 버퍼 flush, 감독 프로세스의 재시작은 각각 구분한다.

TRACE 로그를 켜면 분산 추적이 생기는가?

아니다. TRACE는 로그 심각도 이름이고, 분산 추적은 호출의 span·인과관계·시간을 연결하는 계측이다. 로그와 추적을 연결하려면 trace_id·span_id 맥락의 전달과 계측이 필요하다.

console.error()나 stderr 출력은 자동으로 ERROR 로그인가?

그렇게 보장되지 않는다. 콘솔 메서드나 스트림은 출력 수단이다. 런타임·로깅 라이브러리·수집기가 이를 어떻게 분류하는지에 따라 달라진다. 단순 문자열을 출력했다고 구조화된 level 필드가 자동 생성된다고 가정하지 않는다.

INFO는 항상 성공한 사건인가?

아니다. “작업을 시작했다”, “요청을 받았다”, “정상적인 업무 규칙으로 거절했다”도 INFO일 수 있다. 실제 성공·실패는 outcome 같은 결과 필드와 사건 의미로 확인한다.

ERROR 로그 수를 요청 실패 수로 사용해도 되는가?

대표 로그가 한 번만 남고, 누락·중복·재시도·샘플링·필터를 정확히 처리하며 분모도 정의했다면 지표를 만들 수 있다. 이런 조건 없이 단순 건수를 쓰면 실제 실패율과 다를 수 있다. 사용자 결과를 직접 계측하는 메트릭을 함께 설계한다.

DEBUG가 출력되지 않으면 코드가 실행되지 않은 것인가?

아니다. 유효 로거 레벨, handler·provider, 수집 필터, 저장·검색 조건을 순서대로 확인한다. 레벨 필터 전에 인수를 계산했을 수도 있으므로 출력 여부와 실행·비용을 같은 것으로 보지 않는다.

모든 ERROR를 제거하는 것이 좋은 운영 목표인가?

불필요한 오류와 잘못된 분류를 줄이는 것은 좋다. 하지만 기록 자체를 숨기면 사용자 실패를 알기 어려워진다. 실패율·영향·복구 시간과 알림 품질을 목표로 삼고 로그는 그 사실을 정확히 설명해야 한다.

각주와 출처

공식 정의와 팀에서 정해야 할 정책을 구분한다

아래 공식 자료를 직접 확인하고 한국어로 재구성했다. 레벨 선택 사례·임계값 실습·처리 도식·계산·운영 양식은 교육용 예시다. 특정 제품의 모든 기본 설정과 버전별 차이를 포괄하지 않는다. 확인일: 2026년 11월 25일.

각주

  1. 이름의 차이. TRACE·DEBUG·INFO·WARN·ERROR·FATAL은 흔한 설명용 구분이다. Python은 기본 TRACE가 없으며 WARNING·CRITICAL을 쓴다. Syslog에는 NOTICE·ALERT·EMERGENCY가 있다. [S1] [S3] · 본문으로
  2. 레벨의 정책적 의미. Log4j는 미리 정의한 레벨과 비교 순서를 제공하지만 각 레벨의 사건 분류는 애플리케이션별 정책이 필요하다. 본문의 WARN·ERROR 경계는 그 정책을 논의하기 위한 예시다. [S2] · 본문으로
  3. 치명적 로그와 종료. Python critical()은 레코드를 만드는 로깅 메서드다. 프로세스 종료 API가 아니다. 다른 언어·라이브러리의 fatal 계열 API는 직접 확인한다. 강제 종료·충돌에서 모든 기록이 보존된다는 보장도 별개다. [S1] · 본문으로
  4. Python의 전파. propagate가 참이면 레코드는 조상 로거의 handler로 직접 전달된다. 이 과정에서 조상 로거 자체의 level·filter를 다시 검사하지 않는다. 다른 플랫폼에 이 규칙을 그대로 일반화하지 않는다. [S1] · 본문으로
  5. 로그 데이터 모델. OpenTelemetry는 사건·관측 시각, 원본·정규화 심각도, trace 맥락, 본문·자원·속성을 구분한다. 본문의 JSON 예제는 이 모델의 정확한 wire 형식이 아니다. [S4] · 본문으로
  6. 플랫폼 숫자 비교. Python·.NET·OpenTelemetry와 Syslog·Log4j는 숫자 방향과 값이 다르다. 값이 같거나 이름이 비슷하다는 이유만으로 의미가 같다고 해석하지 않는다. [S1] [S2] [S3] [S4] [S6] · 본문으로
  7. Syslog Priority. RFC 5424의 PRI는 facility와 severity의 조합이다. 소프트웨어 이벤트의 심각도 값 하나와도, 조직의 P0–P4 우선순위와도 다르다. [S3] · 본문으로
  8. 민감정보와 로그 보호. OWASP는 기록 제외 데이터, 정제·인코딩, 필드 일관성, 로깅 실패 시험, 접근·무결성·보존을 다룬다. 구체적인 업무별 수집·보관·감사 요구는 해당 조직의 기준을 추가 확인한다. [S5] · 본문으로
