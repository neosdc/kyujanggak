SSH 역방향 터널 · 단일 웹 서비스 예시

내부 서버가 먼저 연결하면
클라우드가 요청을 전달할 수 있다

웹 사용자는 VM의 HTTPS 443으로 접속한다. 터널의 18080은 VM 내부에서만 접근한다.

예시 주소: service.example.com · 내부 웹 서비스: 10.0.0.20:8080

설치 순서

먼저 도달 경로를 확인하고, 마지막에 도메인을 연결한다

1

주소와 접속 경로 확인

터널 실행 서버에서 10.0.0.20:8080에 접속되는지 확인한다. 같은 서버에서 클라우드 VM의 SSH 포트로 아웃바운드 연결이 가능한지도 확인한다.

2

클라우드 VM 준비

고정 공개 IP를 가진 VM을 만든다. 보안 그룹에서 HTTPS 443을 허용하고 SSH는 가능한 출발지 IP로 제한한다. OS 방화벽에도 같은 규칙을 적용한다.

3

터널 전용 SSH 계정·키 설정

전용 계정과 키를 만든다. VM의 sshd에서 PermitListen 127.0.0.1:18080과 GatewayPorts no로 원격 포워딩을 제한한다.

4

터널 실행·자동 재연결

내부 서버에서 ssh -R을 실행한다. 실패 시 재시작하고 죽은 연결을 감지하도록 서비스 관리자를 설정한다.

5

Nginx·TLS 설정

Nginx가 443에서 인증서를 사용하고 127.0.0.1:18080으로 전달하게 한다. 인증서는 DNS 검증 또는 80 포트 검증으로 발급한다.

6

DNS 전환과 검증

도메인의 A 레코드를 VM 공개 IPv4로 설정한다. IPv6도 구성했다면 AAAA 레코드를 추가한다. 외부망에서 로그인, 리디렉션, 업로드, WebSocket을 확인한다.

순서의 이유 DNS 전환 전에 VM에서 curl로 로컬 터널 포트와 Nginx를 각각 검증하면 장애 위치를 빠르게 좁힐 수 있다.

이 구조에서 -R의 대상 주소 10.0.0.20은 내부 터널 실행 서버 쪽에서 해석·접속된다. 웹 서비스가 터널 실행 서버와 같은 장비에 있다면 127.0.0.1:8080을 쓸 수 있다.

보안 위험

내부 서비스 공개 자체가 가장 큰 보안 변화다

터널 포트를 안전하게 묶어도 외부 사용자는 443을 통해 웹 서비스에 도달한다. 서비스의 인증과 취약점 점검이 먼저 필요하다.

설정의 역할 내부 서버의 ssh -R 127.0.0.1:18080:10.0.0.20:8080이 터널 연결 중 VM의 대기 포트를 만든다. VM의 PermitListen 127.0.0.1:18080은 허용 범위를 정한다. Nginx의 proxy_pass http://127.0.0.1:18080은 그 포트로 요청을 보낸다. proxy_pass의 0.0.0.0 설정을 뜻하는 위험이 아니다.
