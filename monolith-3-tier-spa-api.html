SOFTWARE ARCHITECTURE · MONOLITH + 3-TIER · SPA + API

Monolith + 3-Tier
SPA로 그리고, API로 업무를 처리합니다.

브라우저 SPA → 모놀리식 API → DB로 실행 역할을 나눕니다. 화면은 브라우저에서 구성하고, 업무 규칙은 API 백엔드에서 처리합니다.

이 아키텍처를 읽는 방법

SPA와 API를 분리하고, API의 업무 기능은 함께 배포합니다.

용어정의이 구성에서의 의미
Monolith여러 업무 기능을 하나의 애플리케이션 배포 단위로 묶는 구조회원·상품·주문·재고 기능을 하나의 API 백엔드로 빌드·배포
3-Tier표현·업무·데이터를 분리된 실행 계층으로 구성하는 방식브라우저 SPA / API 애플리케이션 / DB 서버
SPASingle Page Application. 로드한 문서 안에서 JavaScript로 화면 전환과 갱신을 처리하는 웹 앱주문 목록·상세 화면을 브라우저의 라우터와 컴포넌트로 구성
API프로그램 사이의 요청·응답과 데이터 형식을 정한 인터페이스HTTP 요청과 JSON 응답으로 SPA와 업무 백엔드를 연결

SPA와 API는 별도로 빌드·배포할 수 있습니다.
그중 업무 기능을 하나로 묶은 API 백엔드를 Monolith라고 부릅니다. 프런트엔드까지 반드시 같은 산출물에 넣는다는 뜻은 아닙니다.

예시는 브라우저에서 사용하는 주문·재고 관리 서비스입니다. 화면에서 주문을 선택하면 SPA가 API를 호출하고, API는 접근 권한과 업무 규칙을 적용해 DB에서 필요한 데이터를 가져옵니다.

Tier를 세는 기준: 이 문서는 브라우저에서 실행되는 표현 계층, API 업무 계층, DB 데이터 계층을 셉니다. 정적 파일 호스팅·CDN·로드밸런서는 이 역할 구분을 지원하는 인프라로 봅니다. 실제 구성요소와 서버 대수는 이보다 많을 수 있습니다.

MONOLITH · 배포 범위

API 주소가 여러 개여도, 업무 백엔드의 배포 단위는 하나입니다.

/api/members, /api/products, /api/orders가 있어도 같은 API 프로그램이 이 요청들을 모두 처리할 수 있습니다. 주문 모듈이 재고 모듈을 사용할 때는 보통 같은 프로세스 안에서 메서드를 호출합니다.

재고 처리만 수정하더라도 일반적으로 API 백엔드 전체를 새 버전으로 배포합니다. 모듈의 책임과 공개 인터페이스를 명확히 나누면 Modular Monolith로 구성할 수 있습니다.

SPA를 따로 배포하면 무엇을 조율해야 하나요?

두 산출물을 따로 배포하려면 API 계약의 호환성을 관리해야 합니다. 새 API가 열려 있는 브라우저의 이전 SPA 버전과도 통신할 수 있는지 확인합니다. 필드를 갑자기 제거하거나 의미를 바꾸면 배포 시점이 달라진 클라이언트에서 오류가 날 수 있습니다.

프로젝트에 따라 SPA 정적 파일을 API 서버의 산출물에 포함해 함께 배포할 수도 있습니다. 여기서는 두 산출물을 따로 만들 수 있는 구성을 기준으로 설명합니다. 저장소가 하나인지 여러 개인지는 별도의 코드 관리 선택입니다.

SPA · 화면의 실행 위치

처음에는 화면 코드를 받고, 이후에는 필요한 데이터를 받습니다.

처음 접속할 때 브라우저는 HTML과 JavaScript·CSS를 받습니다. JavaScript가 실행되면 화면 컴포넌트를 만들고, 클라이언트 라우터가 주소와 화면 상태를 연결합니다. 목록에서 상세로 이동할 때는 필요한 데이터를 API에서 가져와 화면 일부를 갱신할 수 있습니다.

SPA가 맡는 일

  • 컴포넌트 렌더링과 화면 전환
  • 로딩·빈 결과·오류 상태 표시
  • 폼 입력과 사용자 경험을 위한 검증
  • API 호출 결과를 화면 상태에 반영

API가 최종 판단하는 일

  • 인증과 데이터별 접근 권한
  • 가격·할인·주문 가능 여부 같은 업무 규칙
  • 데이터 변경과 트랜잭션
  • DB에서 읽은 데이터를 응답 형식으로 구성
‘Single Page’는 화면이나 HTML 파일이 하나라는 뜻인가요?

사용자가 보는 화면은 목록·상세·설정처럼 여러 개일 수 있습니다. 핵심은 일반적인 앱 내 이동을 새 문서 전체의 로딩 대신 같은 문서 안의 화면 갱신으로 처리한다는 점입니다. 모든 자원을 처음에 전부 내려받는다는 뜻도 아닙니다. 화면별 코드 분할과 지연 로딩을 사용할 수 있습니다.

예를 들어 /orders/42를 직접 새로고침하면 정적 호스팅이 해당 주소에도 SPA 진입 문서를 제공하도록 설정할 수 있습니다. API 경로와 정적 파일 경로는 별도로 라우팅해야 합니다.

3-TIER · 실행 책임

표현은 SPA, 업무 처리는 API, 저장은 DB가 맡습니다.

실행 계층주요 책임연결 방식
Tier 1 · 브라우저 SPA화면·클라이언트 라우팅·화면 상태·사용자 입력HTTP로 API에 요청하고 JSON을 받아 화면 갱신
Tier 2 · API 백엔드인증·권한·업무 규칙·트랜잭션·응답 데이터 구성DB 드라이버나 ORM을 통해 DB 서버에 접근
Tier 3 · DB 서버영속 데이터·제약 조건·인덱스·트랜잭션과 동시성 관리SQL 등의 요청을 처리하고 결과 반환

브라우저는 DB 접속 정보 대신 API의 주소와 요청·응답 규격을 사용합니다. API 서버가 DB 연결을 관리하고, 요청한 사용자가 해당 주문을 볼 수 있는지 같은 규칙을 적용합니다. 브라우저의 입력 검증은 사용자 경험을 돕고, 서버는 입력과 업무 규칙을 다시 검증합니다.

서버 대수와 Tier 수는 다릅니다. 같은 API 애플리케이션의 인스턴스를 여러 대 실행해도 모두 업무 Tier에 속합니다. DB 복제본이나 여러 브라우저가 있어도 이 설명의 세 역할 구분은 유지됩니다.

API · 업무의 진입점

API는 요청을 업무 처리로 연결하고, 결과를 JSON으로 돌려줍니다.

API 예시의미대표 응답
GET /api/orders조건에 맞는 주문 목록 조회목록 데이터가 담긴 JSON
GET /api/orders/42접근 가능한 특정 주문 조회주문 상세 JSON 또는 오류 응답
POST /api/orders서버가 규칙을 검증해 주문 생성성공 시 201과 주문 식별자가 담긴 JSON

API 계약에는 경로와 메서드뿐 아니라 요청 필드, 응답 필드, 상태 코드, 오류 형식도 포함됩니다. 이 예시에서는 HTTP와 JSON을 사용하지만, API라는 용어 자체가 특정 프로토콜이나 데이터 형식에 한정되지는 않습니다.

JSON 응답은 DB 테이블을 그대로 돌려주는 것인가요?

API는 화면이나 다른 클라이언트가 필요한 데이터를 응답 객체로 구성할 수 있습니다. DB 테이블·Entity와 JSON 필드를 일대일로 고정할 필요는 없습니다. 내부 컬럼 구조를 바꾸더라도 응답 계약을 유지하도록 설계할 수 있습니다.

이 구성의 화면 렌더링은 SPA가 담당합니다. API Handler·Service·Repository의 구분은 백엔드 내부 책임 분리이며, 이것만으로 백엔드 전체를 MVC의 세 요소와 일대일로 대응시키지는 않습니다.

주문 생성 흐름

SPA의 입력이 API의 업무 처리와 DB 변경으로 이어집니다.

주문 저장과 재고 차감을 같은 DB의 트랜잭션으로 묶으면 한쪽만 반영되는 상황을 줄일 수 있습니다. 동시 주문에 대한 재고 정합성에는 조건부 갱신·잠금 같은 동시성 제어도 필요합니다. 외부 결제 API의 결과까지 같은 로컬 DB 트랜잭션으로 되돌릴 수 있는 것은 아닙니다.

실패하거나 응답을 받지 못하면 어떻게 되나요?

API는 권한 부족, 입력 오류, 재고 부족 같은 결과를 상태 코드와 일관된 오류 JSON으로 전달합니다. SPA는 로딩을 끝내고 사용자가 조치할 수 있는 메시지를 표시합니다.

네트워크가 끊겨 응답을 받지 못해도 서버에서는 주문이 생성되었을 수 있습니다. 주문 생성 재시도를 허용한다면 멱등성 키나 중복 방지 제약 등으로 같은 의도가 중복 주문으로 이어지지 않도록 설계합니다.

확장과 운영

API를 복제해 처리량을 늘려도 업무 기능의 배포는 함께 움직입니다.

관점이 구성의 특성설계할 내용
화면과 업무SPA와 API를 별도로 개발·빌드·배포 가능API 계약, 이전 SPA 버전과의 호환성, 캐시 갱신
백엔드 개발업무 모듈 사이를 같은 프로세스에서 호출모듈 의존성, 전체 API의 회귀 검증과 배포 영향
성능·확장정적 파일은 캐시·CDN, API는 여러 인스턴스로 확장 가능브라우저 초기 로딩, 네트워크 지연, API·DB 병목
권한과 접속API에서 권한을 적용하고 DB 연결을 관리HTTPS, 사용자별 데이터 권한, 인증 방식에 맞는 세션·토큰 처리
사용자 경험화면을 부분 갱신하며 입력 상태를 유지 가능로딩·오류·재시도·중복 제출·접근성·주소 직접 진입
CORS와 인증은 어떤 관계인가요?

SPA와 API의 출처가 다르면 브라우저의 교차 출처 정책에 맞춰 CORS를 구성합니다. 같은 출처에서 경로로 구분해 제공하면 구성이 달라집니다. CORS는 브라우저가 응답을 읽는 정책이며, 사용자 인증이나 데이터 접근 권한을 대신하지 않습니다.

쿠키 세션과 토큰 방식 중 무엇을 쓰는지는 별도의 선택입니다. 쿠키를 사용하는 요청은 CSRF 보호 등을, 토큰 방식은 저장·전달·만료 정책 등을 인증 방식에 맞춰 설계합니다.

이 구성을 다시 읽어 보기

SPA와 API를 따로 배포해도 API 백엔드를 Monolith라고 부를 수 있나요?

가능합니다. 이 문서에서 Monolith의 범위는 업무 API 백엔드입니다. 그 안의 회원·상품·주문·재고를 하나의 애플리케이션 배포 단위로 묶습니다.

API의 URL이 많거나 인스턴스가 여러 대면 구조가 바뀌나요?

URL 개수나 인스턴스 수만으로 업무 배포 경계가 바뀌지는 않습니다. 같은 전체 API 애플리케이션을 실행한다면 이 문서의 모놀리식 백엔드 구성이 유지됩니다.

왜 SPA에서 검증한 입력을 API가 다시 확인하나요?

서버의 업무 결과와 접근 권한은 API가 책임지기 때문입니다. 브라우저의 코드는 변경하거나 우회할 수 있으므로 API는 요청한 사용자와 입력에 대해 필요한 검증을 수행합니다.
