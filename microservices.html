Microservices
업무를 서비스로 나누고, 계약으로 연결합니다.

업무별 서비스가 자기 로직과 데이터를 소유하고, 독립적으로 배포할 수 있도록 설계합니다. 서비스 사이의 협력은 네트워크 통신으로 이어집니다.

정의와 핵심 원칙

업무 경계가 실행·배포·데이터의 책임으로 이어집니다.

원칙의미이 예시에서의 모습
업무별 서비스응집된 업무 능력과 규칙을 책임지는 경계주문 생성·진행 상태 / 재고 예약·해제 / 결제 승인·취소
독립 실행·배포호환되는 계약 아래에서 서비스별로 버전을 갱신할 수 있게 설계재고 서비스의 구현을 바꾸고 재고 서비스만 배포
데이터 소유권서비스가 자기 데이터의 변경 규칙과 접근 경로를 책임짐주문 서비스는 재고 DB를 수정하는 대신 재고 API 호출
네트워크 계약API나 메시지의 형식·의미·오류 처리로 협력예약 요청·결과, 결제 요청·결과, 주문 완료 이벤트
운영 책임서비스별 상태를 관측하고 장애·확장·배포를 관리로그·메트릭·추적, 타임아웃, 재시도와 롤백 전략

Microservices는 서비스를 작게 만드는 기법에만 머물지 않습니다. 다른 서비스의 내부 구현을 몰라도 계약으로 협력하고, 변경과 운영의 책임을 업무 경계에 맞추는 것이 중요합니다. 서비스 하나가 여러 API 경로와 내부 모듈을 가질 수 있습니다.

필수 기술이 정해져 있지는 않습니다. Docker·Kubernetes·메시지 브로커·API Gateway는 필요에 따라 선택할 수 있습니다. 서비스 수, 서버 대수, 저장소 개수만으로 아키텍처를 판단하지 않습니다.

서비스 경계와 배포

한 서비스의 변경을 그 서비스의 배포로 마칠 수 있게 설계합니다.

독립 배포는 다른 서비스가 사용하는 계약을 유지할 때 가능합니다. 새 필드를 추가하거나 내부 알고리즘을 바꾸는 변경은 서비스 안에서 처리할 수 있지만, 요청·응답의 의미를 바꾸면 소비자와의 호환성을 관리해야 합니다.

모든 변경에 여러 서비스의 동시 릴리스가 필요하거나 공용 라이브러리 버전을 일제히 올려야 한다면, 배포 경계 사이의 결합을 점검합니다. 저장소는 하나로 관리할 수도, 서비스별로 나눌 수도 있습니다. 코드 저장소와 배포 단위는 같은 개념이 아닙니다.

서비스는 무엇을 기준으로 나누나요?

업무 규칙, 함께 바뀌는 데이터와 기능, 팀의 책임과 변경 주기를 살펴봅니다. 단순히 테이블마다 또는 API 경로마다 서비스를 하나씩 만들면 자주 함께 바뀌는 업무가 여러 네트워크 호출로 흩어질 수 있습니다.

서비스 내부에서는 Controller·Service·Repository, 도메인 모델이나 여러 모듈을 사용할 수 있습니다. 코드가 짧은지보다 책임이 응집되어 있는지, 계약을 지키며 독립적으로 바꿀 수 있는지가 경계 판단에 더 도움이 됩니다.

API와 이벤트

결과가 필요한 요청과 뒤따르는 작업을 구별합니다.

HTTP·gRPC 같은 동기 통신은 필요한 결과를 곧바로 받아 처리하기 쉽습니다. 대신 호출 대상의 지연과 장애가 호출자에게 영향을 줍니다. 요청이 여러 서비스를 연달아 거치면 각 호출의 시간과 실패 가능성이 누적됩니다.

메시지와 이벤트는 후속 처리를 분리하는 데 사용할 수 있습니다. 그만큼 중복 전달, 순서, 재시도, 미처리 메시지와 스키마 호환성을 다뤄야 합니다. 모든 서비스를 비동기로 연결해야 하는 것은 아닙니다.

이벤트를 발행하면 데이터 변경과 전달이 자동으로 보장되나요?

DB에 주문을 저장한 뒤 이벤트를 보내기 전에 프로세스가 종료되면 두 작업의 결과가 달라질 수 있습니다. Outbox 패턴은 업무 변경과 발행할 이벤트 기록을 같은 로컬 DB 트랜잭션으로 저장하고, 별도 전달기가 나중에 브로커로 보냅니다.

전달기가 다시 보내거나 소비자가 다시 처리할 수 있으므로 이벤트 식별자와 중복 처리 방지가 필요합니다. Outbox를 사용한다고 외부 시스템의 모든 부수 효과까지 정확히 한 번 실행되는 것은 아닙니다.

서비스별 데이터 소유권

데이터 변경은 그 데이터를 소유한 서비스가 책임집니다.

주문 서비스가 재고 테이블을 직접 수정하면 재고 규칙과 저장소 구조에 결합됩니다. 재고 API로 예약을 요청하거나, 공개된 이벤트를 통해 필요한 사본을 유지하는 방식으로 소유권을 지킬 수 있습니다. 같은 DB 클러스터를 사용하면 자원과 장애의 영향은 여전히 공유할 수 있습니다.

서비스마다 로컬 트랜잭션이 있어도, 전체 주문이 하나의 트랜잭션인 것은 아닙니다.
재고 예약이 커밋된 뒤 결제가 실패할 수 있습니다. 서비스 사이의 진행 상태와 복구 절차를 따로 설계합니다.

여러 서비스의 데이터를 합쳐 보여 주려면 어떻게 하나요?

API 조합으로 데이터를 조회하거나, 이벤트·CDC 등으로 조회 전용 모델을 만들 수 있습니다. API 조합은 호출 대상의 지연·가용성에, 복제된 조회 모델은 데이터 갱신 지연과 재구성 절차에 영향을 받습니다.

서비스 간 복제 데이터는 최종 일관성을 선택할 수 있습니다. 이때 전달·재시도·중복 처리·대사 절차가 있어야 원하는 상태에 수렴할 수 있습니다. ‘최종 일관성’이라는 이름만으로 자동 복구가 보장되지는 않습니다. 각 서비스 내부의 일관성 수준은 DB와 트랜잭션 설계에 따라 달라집니다.

서비스 간 주문 처리

전체 작업은 여러 서비스의 로컬 커밋으로 진행됩니다.

서비스를 넘는 작업에는 진행 상태와 실패 시의 대응을 정해야 합니다. Saga는 여러 로컬 트랜잭션으로 이어지는 작업을 진행하고 필요할 때 보상 작업을 수행하는 패턴입니다. 주문 서비스 같은 조정자가 흐름을 관리할 수도 있고, 서비스들이 이벤트를 구독하며 협력하도록 설계할 수도 있습니다.

어떤 방식이든 상관관계 식별자, 멱등성, 상태 전이, 재시도와 미완료 작업의 복구를 관리해야 합니다. Saga를 도입하는 것만으로 전체 작업이 하나의 ACID 트랜잭션이 되지는 않습니다.

실패와 보상

일부 서비스의 작업이 성공한 뒤에도 전체 주문은 실패할 수 있습니다.

결제가 거절되면 이미 커밋된 재고 예약을 DB 롤백으로 지우는 대신, 재고 서비스에 예약 해제를 요청합니다. 결제가 성공한 뒤 다른 작업이 실패했다면 상황에 따라 환불 같은 다른 보상이 필요할 수 있습니다. 보상은 새로운 업무 작업이므로 실패하거나 지연될 수 있고, 원래의 모든 부수 효과를 되돌리는 것도 아닙니다.

타임아웃은 ‘실패 확정’이 아니라 결과를 모르는 상태일 수 있습니다.
응답이 유실되어도 상대 서비스는 처리했을 수 있습니다. 상태 조회·멱등성 키·대사 절차로 결과를 확인하고 다음 행동을 결정합니다.

같은 요청이나 메시지를 다시 보내도 되나요?

주문 생성·결제처럼 중복 효과가 생기면 안 되는 작업은 같은 업무 의도를 식별하는 멱등성 키를 사용할 수 있습니다. 서비스는 처리 결과를 기록하고 동일 요청의 재실행 정책을 정의합니다. 메시지 소비자도 중복 전달에 대비합니다.

재시도는 횟수·시간 예산을 제한하고 지연과 jitter를 적용할 수 있습니다. 모든 오류를 무조건 재시도하면 부하가 커지거나 중복 처리가 생길 수 있습니다. 명확한 거절과 일시 장애, 결과 불명을 구별합니다.

확장과 운영

서비스별 자율성에는 서비스 사이의 실패를 다루는 책임이 따릅니다.

관점이 구성에서 얻는 점설계·운영할 내용
변경·배포호환 계약 아래에서 서비스별 릴리스 가능API·이벤트·DB 변경의 호환성, 점진 배포와 복구
확장부하가 큰 서비스를 중심으로 실행본 추가 가능실제 병목, DB·브로커 용량과 비용, 연결·동시 요청 제한
장애 대응프로세스·자원 경계를 서비스별로 구성 가능타임아웃, 회로 차단, 격리·부하 제한으로 장애 전파 제어
데이터서비스가 자기 업무 규칙과 저장소 변경을 책임짐로컬 트랜잭션, 복제 데이터 갱신 지연, 보상·대사
관측서비스별 지연·오류·자원 상태를 확인 가능상관관계 ID, 분산 추적, 메트릭·로그와 경보
팀과 품질업무 책임에 맞춰 서비스 소유권을 나눌 수 있음자동 빌드·배포, 계약·통합 검증, 호출 관계와 운영 책임

프로세스를 나누어도 서비스가 동기 호출로 연결되면 장애가 전파될 수 있습니다. 회로 차단기는 실패가 누적된 대상에 대한 호출을 잠시 제한하고, 자원 격리와 동시 요청 제한은 한 의존 대상이 전체 자원을 소진하는 상황을 줄이는 데 사용합니다.

서비스 경계를 명확히 할 수 있고 독립 배포·확장의 필요가 있으며, 이를 관측하고 운영할 여건이 있을 때 장점이 커집니다. 필요한 서비스 수와 경계는 업무의 변경 패턴과 팀의 운영 능력을 보며 조정합니다.

API Gateway와 서비스별 기술 선택은 필수인가요?

Gateway나 BFF는 클라이언트의 진입 경로, 인증 연계, 라우팅과 응답 조합 등에 사용할 수 있습니다. 모든 시스템에 필수는 아니며, 핵심 업무 규칙을 한곳으로 다시 모으지 않도록 책임을 정합니다.

서비스별로 다른 언어와 DB를 선택할 수 있지만 반드시 달라야 하는 것은 아닙니다. 기술 종류가 늘면 배포·관측·보안 업데이트와 인력 운영의 부담도 늘어납니다.

이 구성을 다시 읽어 보기

주문·재고 코드를 HTTP로 연결하면 독립 배포가 완성되나요?

네트워크 분리는 실행 경계의 일부입니다. 호환되는 계약과 데이터 소유권을 유지하고, 다른 서비스의 동시 변경 없이 자기 서비스를 배포할 수 있도록 의존성을 설계해야 합니다.

서비스마다 물리 DB 서버가 반드시 한 대씩 있어야 하나요?

그렇지는 않습니다. 핵심은 논리적인 데이터 소유권과 접근 경계입니다. 같은 DB 인프라를 사용하면 자원·장애·운영의 결합이 남는다는 점도 함께 고려합니다.

결제 요청이 타임아웃되면 바로 다시 결제하면 되나요?

상대 서비스가 이미 처리했을 수 있습니다. 같은 멱등성 키, 결과 조회와 상태 대사를 사용해 중복 효과를 막으면서 결과를 확인해야 합니다.
