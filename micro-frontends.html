SOFTWARE ARCHITECTURE · MICRO-FRONTENDS

Micro-frontends
업무별 프런트엔드를 하나의 제품으로 조합합니다.

상품·주문·회원 같은 업무 영역별로 프런트엔드를 나누고, 각 팀이 개발·배포를 책임질 수 있도록 구성합니다. 사용자에게는 하나의 제품 경험을 제공합니다.

정의와 적용 범위

프런트엔드의 업무 경계가 팀의 변경·배포 책임으로 이어집니다.

요소의미주문 관리 제품의 예
업무별 프런트엔드응집된 화면·상태·사용자 흐름을 책임지는 애플리케이션 단위주문 목록·상세·취소 흐름을 주문팀이 소유
Shell / Host업무 앱을 연결하는 공통 프레임과 조합 책임내비게이션, 경로 연결, 앱 로딩과 공통 오류 화면
조합 계약앱의 로딩·실행·종료·이동·이벤트 방식을 정한 약속mount·unmount, 이동 콜백, 공개 이벤트
독립 배포호환 계약 아래에서 각 업무 앱의 릴리스를 분리할 수 있도록 설계주문 앱을 새 버전으로 게시하고 로딩 대상을 전환
제품 공통 규칙여러 팀의 결과가 일관된 제품으로 보이게 하는 약속디자인 시스템, 접근성, 인증 연계와 관측 규칙

컴포넌트 라이브러리는 버튼·폼 같은 UI를 재사용하는 단위입니다. Micro-frontend는 주문 관리처럼 업무 화면과 사용자 흐름의 변경·배포 책임을 나누는 단위로 생각하면 좋습니다. 하나의 업무 앱 안에 여러 컴포넌트와 화면이 들어갑니다.

백엔드 구성은 별개의 선택입니다. Micro-frontends 뒤에 하나의 모놀리식 API를 둘 수도, 여러 Microservices를 둘 수도 있습니다. 프런트엔드 앱과 백엔드 서비스를 반드시 일대일로 대응시킬 필요는 없습니다.

여러 번들로 나누는 것만으로 팀과 배포의 자율성이 완성되지는 않습니다.
공개 계약과 공통 의존성을 관리하고, 다른 앱의 내부 변경 없이 자기 앱을 갱신할 수 있도록 설계합니다.

독립 빌드와 배포

업무 앱의 배포와 Shell의 배포를 분리할 수 있습니다.

Shell이 안정된 앱 로딩 계약을 사용하면 주문팀은 주문 앱을 새 버전으로 게시하고 로딩 대상을 바꿀 수 있습니다. Shell 코드가 매번 다시 빌드되어야 하는 구조인지, 로딩 설정만 갱신할 수 있는 구조인지는 별도로 설계합니다.

이미 열려 있는 브라우저가 새 배포를 즉시 사용하는 것은 아닙니다. 현재 로드한 버전과 캐시가 남을 수 있으므로 이전 앱·Shell·API 사이의 호환성, 구버전 자원의 유지 기간과 복구 절차를 관리합니다.

배포할 때 어떤 점을 맞춰야 하나요?

새 자원을 먼저 게시하고 무결성과 로딩을 확인한 뒤 버전 매핑을 전환하는 식으로 배포할 수 있습니다. 이전 버전으로 되돌릴 수 있도록 자원과 설정을 함께 관리합니다. 캐시된 진입 파일이 삭제된 청크를 가리키지 않도록 정책을 정합니다.

독립 배포가 모든 변경의 무조율 배포를 뜻하지는 않습니다. Shell과 앱의 생명주기 계약, 디자인 시스템, 공용 라이브러리와 API를 바꾸면 호환성을 검증해야 합니다. 저장소는 하나로 관리해도, 팀별로 나눠도 됩니다.

조합 방식

제품의 요구에 따라 화면을 합치는 위치와 방법을 고릅니다.

방식조합하는 방법주요 고려 사항
경로·페이지 단위경로에 따라 업무 앱이나 페이지로 연결경계가 명확함. 전체 문서 이동인지 클라이언트 전환인지 구분
브라우저 런타임 조합Shell이 업무 앱의 코드를 로드해 같은 페이지에서 실행로딩·종료 계약, 공유 라이브러리, CSS와 오류 영향
서버·엣지 조합서버나 엣지에서 화면 조각·응답을 조합렌더링·캐시·하이드레이션·실패 시 대체 응답의 계약
iframe 조합별도 문서로 업무 화면을 넣고 메시지 등으로 연결문서·출처 경계, 높이·이동·인증·접근성·통신 정책
빌드 시 패키지 결합팀별 UI 패키지를 Host 빌드에 포함개발 책임은 나눌 수 있지만 변경 반영에 Host 재빌드·배포가 필요할 수 있음

Module Federation, import maps, Web Components 등은 브라우저 조합을 구현할 때 사용할 수 있는 도구나 표준입니다. 이 중 특정 기술을 사용해야 Micro-frontends가 되는 것은 아닙니다. 기술 자체가 배포 호환성·스타일 격리·성능을 모두 해결하지도 않습니다.

이후 그림은 경로 기반 Shell + 런타임 업무 앱 로딩 예시에 집중합니다. 상품·주문·회원 화면은 여러 개이며, 각 업무 앱도 자체 라우팅과 상태를 가질 수 있습니다.

경로 이동부터 화면 표시까지

Shell이 업무 앱을 선택하고, 업무 앱이 자기 화면을 구성합니다.

업무 앱에서 나갈 때는 종료 계약도 중요합니다. 이벤트 구독, 타이머, 전역 리스너와 화면 자원을 정리하고 진행 중인 요청의 결과가 사라진 화면을 갱신하지 않도록 처리합니다. 직접 URL 진입·새로고침·뒤로 가기도 같은 경로 계약에 맞춰 동작해야 합니다.

최소한 어떤 실행 계약을 정하나요?
mount(container, context)
  context.basePath       앱이 담당할 경로
  context.navigate       제품 내 이동을 요청하는 함수
  context.locale         표시 언어 등 공개된 제품 정보

unmount()
  이벤트 구독·타이머·리스너·화면 자원 정리

특정 라이브러리의 실제 API가 아닌 개념 예시입니다. 앱의 준비 완료와 오류 전달, 경로 갱신, 자원 정리의 책임을 명시하고 계약 검증에 포함할 수 있습니다.

라우팅과 상태 계약

다른 앱의 내부 상태보다 공개된 이동·이벤트 계약을 사용합니다.

계약 영역정할 내용결합을 줄이는 방향
URL과 라우팅앱별 경로 소유권, 이동·뒤로 가기·직접 진입다른 앱의 내부 라우터를 직접 조작하기보다 공개 이동 계약 사용
이벤트이름, 의미, 데이터 형식, 발행 시점과 구독 해제업무 Entity 전체 대신 식별자·변경 사실 등 필요한 정보 전달
상태상태별 소유 앱, 서버 원본과 화면 사본의 관계모든 앱의 업무 상태를 하나의 전역 Store로 묶지 않도록 범위 제한
제품 공통 정보언어·테마·사용자 표시 정보 등 전달 방식Shell의 공개 컨텍스트를 작고 안정적으로 유지
인증·권한인증 연계, 요청 자격 증명과 만료·로그아웃 처리브라우저의 표시 여부와 별개로 API가 데이터 접근 권한을 확인

이벤트가 많아지면 누가 발행하고 어떤 앱이 구독하는지 추적하기 어려워질 수 있습니다. 이벤트 목록과 소유자, 호환성 규칙을 관리합니다. 같은 페이지에서 앱을 조합하는 구조는 그 자체로 보안 경계가 아니므로, 이벤트 버스에 비밀 정보를 무분별하게 공유하지 않습니다.

스타일과 실행 영향

배포를 나눠도 같은 페이지의 영향 범위는 따로 관리해야 합니다.

전역 CSS가 다른 앱의 화면을 바꾸거나, 전역 변수와 리스너가 충돌하거나, 무거운 JavaScript 작업이 페이지 응답성을 떨어뜨릴 수 있습니다. 네트워크 로딩 실패는 대체 화면으로 다룰 수 있어도 공유 실행 환경의 모든 문제를 같은 방식으로 격리할 수 있는 것은 아닙니다.

영역사용할 수 있는 방법확인할 한계
스타일CSS Modules, 이름 규칙, 범위 제한, Shadow DOM 등전역 선택자·상속·CSS 변수 등 남아 있는 영향 범위
앱 오류로딩·초기화 실패 감지, 대체 UI, 프레임워크별 오류 경계비동기 오류·전역 오류·실행 지연까지 모두 포착하는지 구분
의존 라이브러리중복 허용 또는 호환 버전 공유, Singleton 정책전송 크기와 버전 제약·런타임 호환성 사이의 비용
별도 문서iframe과 명시적 메시지 계약출처·메시지 검증, 탐색·포커스·높이·인증 연계와 접근성
업무 앱마다 다른 프레임워크를 써도 되나요?

가능한 조합 방식이 있지만 반드시 달라야 하는 것은 아닙니다. 같은 기술을 사용하면 디자인 시스템·공통 라이브러리·관측과 채용·운영을 단순하게 유지하기 쉽습니다. 여러 프레임워크가 필요하면 코드 크기, 로딩·종료 방식과 UI 일관성을 함께 관리합니다.

Module Federation의 공유 의존성 설정은 패키지 로딩과 버전 협상의 문제를 다룹니다. CSS 격리, 앱의 접근 권한과 모든 런타임 오류를 함께 해결하는 기능으로 보아서는 안 됩니다.

제품 운영과 품질

팀의 배포 자율성과 하나의 제품 품질을 함께 유지합니다.

관점기대할 수 있는 점설계·운영할 내용
팀과 릴리스업무 화면의 변경·배포 책임 분리경계·소유자·공통 계약, 매니페스트와 자원의 점진 배포·복구
제품 경험여러 팀의 기능을 한 프레임과 이동 흐름으로 연결디자인 시스템, 일관된 오류·로딩 화면, 접근성과 탐색
성능경로에 필요한 업무 앱과 코드만 로드 가능진입·전환 시간, 중복 라이브러리, 캐시·프리패치와 성능 예산
검증팀별 앱 검증과 계약 중심의 조합 검증 가능호스트·앱·API 버전 조합, 주요 사용자 흐름과 직접 진입
관측앱별 오류·로딩·버전 상태를 추적 가능앱 식별자·버전·상관관계 정보, 소스맵과 사용자 영향 확인

독립적으로 바뀌는 업무 영역과 여러 팀의 릴리스 필요가 클 때 효과가 커질 수 있습니다. 경계가 자주 얽히거나 제품 규모에 비해 조합·공유 의존성 관리가 더 크다면 분리 범위를 조정할 수 있습니다. 처음부터 가능한 한 잘게 나누는 것이 목표는 아닙니다.

이 구성을 다시 읽어 보기

Microservices를 사용해야 Micro-frontends를 적용할 수 있나요?

그렇지는 않습니다. 업무별 프런트엔드가 하나의 백엔드 API를 사용할 수도 있습니다. 프런트엔드의 소유·조합 경계와 백엔드 서비스 경계는 함께 설계하되 반드시 일대일 대응시키지는 않습니다.

코드를 여러 패키지로 나누고 Host를 항상 다시 배포하면 어떤가요?

개발 책임과 코드 경계는 나눌 수 있습니다. 실제 배포 독립성은 조합 방식에 따라 달라지므로, 팀이 필요한 수준의 자율성을 얻는지 확인해야 합니다.

각 앱을 따로 배포하면 오류와 스타일도 자동으로 격리되나요?

같은 페이지에서 실행되면 공유 DOM·스타일·전역 환경과 실행 시간의 영향이 남을 수 있습니다. 스타일 범위, 오류 대응, 의존성 정책과 조합 방식을 별도로 설계합니다.
