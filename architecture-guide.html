SOFTWARE ARCHITECTURE · MONOLITH + 2-TIER + MVC

Monolith + 2-Tier + MVC
한 프로그램 안의 MVC, 분리된 DB

화면과 업무 기능을 하나의 애플리케이션으로 묶고, 별도 DB 서버에 연결하는 구조를 살펴봅니다.

하나의 아키텍처를 읽는 방법

세 용어가 합쳐져 이 구성의 특징을 설명합니다.

용어정의이 아키텍처에서의 의미
Monolith여러 업무 기능을 하나의 애플리케이션 배포 단위로 묶는 구조회원·상품·주문·재고·화면을 하나의 프로그램으로 빌드하고 배포
2-Tier시스템을 서로 통신하는 두 실행 계층으로 나누는 구조Tier 1: 클라이언트 애플리케이션 / Tier 2: DB 서버
MVCModel·View·Controller로 애플리케이션 내부의 책임을 나누는 패턴Tier 1 안에서 업무 상태·화면·입력 처리를 분리

예시는 사내 주문·재고 관리 프로그램입니다. 직원 PC에 설치된 프로그램이 화면과 업무 처리를 맡고, 여러 직원이 같은 DB 서버의 데이터를 사용합니다. 이 문서는 이 구성 하나를 따라가며 각 용어가 실제로 어떻게 적용되는지 설명합니다.

Tier를 세는 범위: 여기서는 클라이언트 프로그램과 DB 서버를 두 Tier로 셉니다. 서버 대수나 코드 폴더 수가 기준은 아닙니다. 웹 인프라에서 브라우저를 제외하고 ‘앱 서버 + DB 서버’를 2-Tier라고 부르는 용례와는 범위를 구별합니다.

MONOLITH

화면과 업무 기능을 한 프로그램으로 배포합니다.

회원·상품·주문·재고 기능과 각 기능의 화면을 하나의 애플리케이션으로 묶습니다. 주문 처리 중 재고 기능이 필요하면 같은 프로그램 안에서 메서드를 호출합니다. 주문 기능을 수정하면 일반적으로 프로그램 전체를 새 버전으로 빌드하고 배포합니다.

개발과 처리가 단순합니다.

  • 하나의 프로그램을 실행합니다. 화면과 주요 업무 기능을 함께 사용할 수 있습니다.
  • 업무 기능을 내부 호출로 연결합니다. 주문과 재고 사이에 별도의 네트워크 API가 없어도 됩니다.
  • 트랜잭션을 묶기 쉽습니다. 같은 DB 트랜잭션 안의 주문 저장과 재고 차감을 함께 확정하거나 취소할 수 있습니다.

변경과 장애의 범위가 묶입니다.

  • 배포가 함께 움직입니다. 화면이나 업무 규칙의 작은 수정도 전체 프로그램 업데이트로 이어집니다.
  • 회귀 검증이 필요합니다. 공통 코드 변경이 다른 업무 기능에 영향을 줄 수 있습니다.
  • 프로세스 자원을 공유합니다. 한 기능의 메모리 고갈이 같은 프로그램의 다른 기능에 영향을 줄 수 있습니다.
Monolith 안에서도 모듈을 명확하게 나눌 수 있나요?

가능합니다. 모듈별 책임과 공개 인터페이스를 분명히 나누면서 하나로 배포하는 구성을 Modular Monolith라고 부릅니다. 주문 모듈이 재고 테이블을 직접 수정하기보다 재고 모듈의 인터페이스를 사용하도록 설계하는 식입니다.

Monolith는 배포 단위를 설명하므로 코드 품질을 자동으로 결정하지는 않습니다. 모듈 경계, 테스트와 의존성 관리는 별도로 설계합니다. 외부 결제 API의 결과까지 일반적인 로컬 DB 트랜잭션으로 되돌릴 수 있는 것도 아닙니다.

배포와 사용

여러 직원이 같은 프로그램과 DB를 사용합니다.

Monolith의 ‘하나’는 애플리케이션의 배포 단위를 가리킵니다. 실제 설치본이나 사용자가 하나라는 뜻은 아닙니다. 프로그램을 업데이트할 때 각 PC에 새 버전을 배포하는 방법과 구버전 프로그램의 DB 호환성을 함께 관리합니다.

여러 직원이 같은 재고를 동시에 변경할 수 있으므로, 각 프로그램의 화면 확인만으로 데이터 정합성을 보장할 수는 없습니다. DB 트랜잭션, 제약 조건과 적절한 동시성 제어를 함께 적용합니다.

2-TIER

화면·업무 처리와 데이터 저장을 두 Tier로 나눕니다.

직원이 주문을 선택하면 클라이언트 프로그램이 주문 조회 작업을 실행합니다. Model 쪽 저장소 코드가 DB 드라이버를 통해 SQL을 보내고, DB 서버가 결과를 돌려줍니다. 중간에 별도의 업무 처리 서버를 두지 않는 구성입니다.

실행 계층주요 책임이 예시에서 실행되는 것
Tier 1 · 클라이언트화면 표시, 입력 처리, 업무 규칙, DB 접근 요청View·Controller·도메인·Service·Repository·DB 드라이버
Tier 2 · DB 서버데이터 저장·조회, 제약 조건, 트랜잭션과 동시성 관리DBMS, 테이블·인덱스·제약 조건·트랜잭션 처리
업무 로직은 반드시 모두 클라이언트에 있나요?

이 예시에서는 주요 업무 로직을 클라이언트 프로그램에 둡니다. 2-Tier라는 용어 자체가 모든 로직의 위치를 강제하지는 않습니다. DB 저장 프로시저나 제약 조건에 일부 규칙을 둘 수도 있습니다.

‘두 Tier’는 두 대의 컴퓨터나 두 개의 클래스라는 뜻도 아닙니다. 클라이언트와 DB의 실행 역할을 구분한 것입니다. 사용자가 늘면 DB 연결 수, 쿼리 부하와 클라이언트별 권한 관리도 함께 고려합니다.

LAYER · 코드 안의 책임 구분

내부 계층을 나눠도 전체 구성은 2-Tier입니다.

Layer는 코드의 논리적 책임, Tier는 분리된 실행 계층입니다. Controller·Service·Repository가 각기 다른 클래스나 패키지여도 같은 클라이언트 프로그램 안에서 실행된다면, 이 코드 구분만으로 Tier가 추가되지는 않습니다.

MVC와 이 계층 구분도 정확히 일대일 대응하지 않습니다. Controller는 입력 흐름을 연결하고, Service·도메인·Repository는 Model 역할의 수행에 협력합니다. View는 결과를 보여 주는 별도의 역할입니다.

MODEL · VIEW · CONTROLLER

MVC는 업무 상태·화면·입력 처리를 분리합니다.

역할맡는 책임주문 조회 화면의 예
Model업무 상태와 규칙을 표현하고 변경한다. 필요한 데이터 접근과 협력한다.주문, 주문 상태 규칙, 주문 조회 서비스와 저장소 협력
View전달받은 데이터를 사용자가 읽을 형태로 표현한다.주문 목록·상세 창, 금액·상태를 표시하는 UI
Controller입력을 해석하고 적절한 Model 작업과 화면 흐름을 연결한다.주문 선택 이벤트 → 조회 요청 → 상세 화면 갱신
MODEL의 범위

Model은 데이터베이스 자체가 아닙니다.
DB는 Tier 2의 저장 기반이고, Model은 Tier 1에서 상태와 업무 규칙을 다루는 역할입니다.

Controller는 흐름을 연결합니다.

사용자 입력 해석, 입력 형식 확인, 유스케이스 호출과 화면 갱신에 집중합니다. 할인 계산이나 주문 상태 전이 규칙은 Model 쪽에서 다룹니다.

View는 표현에 집중합니다.

금액 형식이나 조건부 표시 같은 표현 로직은 둘 수 있습니다. 주문 가능 여부나 최종 결제 금액처럼 업무 결과를 결정하는 규칙은 Model 쪽에서 다룹니다.

Model은 하나의 Entity나 특정 폴더를 뜻하나요?

MVC의 Model은 개념적인 역할입니다. 실제 구현에서는 도메인 객체, 서비스, 저장소가 협력해 이 역할을 구성할 수 있습니다. DB 테이블에 매핑된 Entity 하나가 Model 전체를 대표하는 것은 아닙니다.

Service와 Repository는 MVC의 필수 구성 요소는 아닙니다. MVC와 계층형 설계를 함께 적용할 때 자주 사용하는 책임 분리입니다. 또 프레임워크에 따라 Controller가 View를 갱신하거나 Model의 변경 알림을 View가 구독할 수 있으므로, 특정 호출 순서를 모든 MVC 구현의 규칙으로 보지는 않습니다.

주문 선택부터 화면 갱신까지

MVC 내부 호출과 Tier 사이의 통신이 이어집니다.

이 흐름에서 Monolith는 MVC와 업무 기능이 한 프로그램으로 배포된다는 점에, 2-Tier는 DB 호출이 실행 경계를 넘는다는 점에, MVC는 사용자 이벤트가 화면·흐름 제어·업무 처리로 나뉜다는 점에 드러납니다.

클라이언트의 코드는 어떤 모양인가요?
// Controller: 입력 이벤트와 화면 흐름을 연결
void onOrderSelected(long orderId) {
    OrderDetail detail = orderQueryService.findVisibleOrder(orderId);
    orderView.showOrder(detail);
}

// Model 쪽 Service: 조회 유스케이스를 수행
OrderDetail findVisibleOrder(long orderId) {
    return orderRepository.findDetail(orderId);
}

// Repository: DB 드라이버를 통해 SQL 조회
// View: 전달받은 주문 번호·금액·상태를 UI에 표시

특정 프레임워크에 종속되지 않은 의사 코드입니다. 실제 화면 응답성을 위해 DB 작업을 UI 스레드 밖에서 처리하고, 결과를 UI에 반영하는 방식은 별도로 구현합니다. 인증·권한·오류 처리도 생략했습니다.

이 조합의 특성과 운영

한 프로그램의 단순함과 DB 공유의 부담을 함께 봅니다.

관점이 구성에서 얻는 점함께 관리할 점
개발·배포화면과 업무 기능을 한 프로젝트에서 구현하고 하나로 패키징새 프로그램을 각 사용자 PC에 배포하고 버전을 관리
변경업무 모듈 사이를 같은 프로그램의 내부 호출로 연결공통 코드 변경의 영향과 전체 회귀 검증
데이터여러 사용자가 DB 서버의 같은 데이터를 사용DB 연결·권한, 스키마 변경과 클라이언트 호환성
동시 사용각 PC에서 화면과 업무 처리를 실행동시 수정, 트랜잭션, DB 제약 조건과 잠금 전략
운영 환경제한된 사용자와 통제된 사내 환경에서 구성이 단순사용자가 많아질 때 DB 부하와 설치본 관리 비용

이 아키텍처는 화면과 업무 처리를 한 프로그램에 담고, 데이터를 DB 서버에서 공유하는 방식입니다. 프로그램 내부를 MVC와 모듈 경계로 정돈하면서도 배포 단위와 실행 Tier의 구성을 유지할 수 있습니다.

이 구성을 다시 읽어 보기

하나의 MVC 프로그램이 별도 DB 서버에 직접 연결한다면?

이 문서의 Monolith + 2-Tier + MVC 구성입니다. Monolith는 애플리케이션 배포 단위, 2-Tier는 클라이언트와 DB의 실행 경계, MVC는 클라이언트 내부의 역할을 설명합니다.

직원 PC가 여러 대이고 각 프로그램 안에 클래스가 많아도 2-Tier인가요?

이 구성에서는 그렇습니다. 여러 PC는 같은 클라이언트 Tier의 설치본이고, 프로그램 안의 클래스 구분은 새로운 Tier를 만들지 않습니다. 별도 DB 서버가 데이터 Tier를 맡습니다.

DB가 별도로 실행되어도 Monolith라고 부를 수 있나요?

가능합니다. 이 문서에서 Monolith는 화면과 업무 기능을 묶은 애플리케이션의 배포 단위를 가리킵니다. 그 애플리케이션이 사용하는 DB 서버는 별도로 운영할 수 있습니다.
