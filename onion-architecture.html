Onion Architecture
도메인 모델을 의존성의 중심에 둡니다.

상태와 업무 규칙을 가진 도메인 모델을 중심에 두고, UI·DB·프레임워크가 안쪽 정책에 의존하도록 구성하는 구조입니다.

DOMAIN AT THE CENTER

도메인 모델을 중심에 두고 데이터베이스를 바깥으로 보냅니다.

Onion Architecture는 Jeffrey Palermo가 2008년에 소개했습니다. 핵심 규칙은 코드는 더 안쪽 계층에 의존할 수 있고, 안쪽 코드는 바깥 계층에 의존하지 않는다는 것입니다. 바로 옆 계층만 참조해야 한다는 뜻은 아닙니다.

영역책임주문 예시
Domain Model업무 개념의 상태와 행동, 항상 지켜야 하는 규칙Order가 양수 수량과 유효한 주문 상태를 보장
Domain Services개별 Entity에 자연스럽게 속하지 않는 업무 정책여러 주문·고객 정책을 고려하는 할인 자격 판단
Application Services한 유스케이스를 실행하도록 작업을 조정사용자 권한 확인 → 모델 생성 → 저장 → 결과 구성
Infrastructure저장·외부 API·메시지·시계 등 기술 구현Postgres Repository, 결제 공급자 Client
UI / Tests사람·외부 시스템·테스트와 핵심을 연결Controller·화면·유스케이스 자동화 테스트
중첩 도형을 읽는 법

각 영역은 정책과 의존성의 경계입니다. 한 프로세스 안에 모두 둘 수 있고, 원의 개수만큼 서버나 서비스를 만들 필요는 없습니다.

Domain Model과 ORM Entity는 같은 개념인가요?

Domain Model은 업무의 상태와 행동을 표현합니다. ORM Entity는 저장 도구의 매핑 단위입니다. 같은 클래스를 사용할 수도 있지만, ORM 특성·Lazy Loading·Session·DB 자료형이 업무 규칙을 지배한다면 경계를 다시 봐야 합니다.

이 문서는 풍부한 도메인 모델을 예로 들지만 Onion을 적용하려고 DDD의 모든 패턴을 도입할 필요는 없습니다. 핵심은 바깥 기술이 안쪽 정책을 지배하지 않도록 하는 것입니다.

안쪽 의존성 규칙

Repository 구현은 바깥에, 그 계약은 정책이 소유하는 안쪽에 둡니다.

원문은 Repository 인터페이스를 도메인에 가까운 핵심에 두고 구현을 바깥에 두는 구성을 설명합니다. 실제 계약의 위치는 어느 정책이 그 능력을 소유하고 사용하는지에 맞춥니다. 모든 Port를 무조건 Domain 폴더에 넣는다는 규칙은 아닙니다.

Domain이 외부 조회 결과를 필요로 하면 어떻게 하나요?

Application Service가 필요한 데이터를 Port로 읽어 Domain에 값으로 전달할 수 있습니다. 정책이 외부 능력을 직접 요구한다면 안쪽에 적절한 추상화를 두는 방법도 있습니다. Domain 객체가 ORM Session이나 HTTP Client를 직접 가져오는 방식은 피합니다.

순환 참조가 생기면 인터페이스 파일을 옮기는 것만으로 해결하지 않습니다. 계약이 누구의 언어인지, 반환 데이터가 어느 계층의 자료형인지 함께 확인합니다.

Application Service

필요한 정보를 얻고, 도메인 행동을 호출하고, 결과를 저장합니다. 도메인 규칙을 같은 서비스에 모두 몰아넣으면 모델은 데이터 운반 역할만 남기 쉽습니다.

Domain Service

도메인 언어로 표현되는 판단을 수행합니다. 저장·로깅·메일 기능이라는 이유만으로 Domain Service라고 부르지 않습니다.

입력 검증과 도메인 검증은 중복 아닌가요?

Controller는 필수 필드·JSON 형식 같은 전송 형식을 검사합니다. Domain은 수량·통화·상태 전이 같은 업무의 유효성을 지킵니다. 사용자에게 빠르게 오류를 보여 주기 위한 UI 검증이 있어도, 업무 규칙을 최종 적용하는 경계의 검증은 필요합니다.

주문 생성의 실행 흐름

도메인은 유효한 주문을 만들고, 애플리케이션은 저장까지 조정합니다.

주문 취소는 어디에 구현하나요?
class Order {
  cancel() {
    if (this.status === "SHIPPED") throw new AlreadyShipped()
    this.status = "CANCELLED"
  }
}
class CancelOrderService {
  constructor(private orders: OrderRepository) {}
  execute(request) {
    const order = this.orders.get(request.orderId)
    authorizeCancellation(request.actor, order)
    order.cancel()
    this.orders.save(order)
    return { orderId: order.id, status: order.status }
  }
}

생성 예시와 같은 원칙을 취소 유스케이스에 적용한 의사 코드입니다. 실제 구현은 조회·변경·저장을 한 트랜잭션과 동시성 정책 안에서 수행합니다. 배송 상태가 동시에 바뀌는 경우 버전 검사나 잠금 등도 필요합니다.

모델과 데이터의 경계

도메인 모델의 독립성은 자료형과 동작에서도 드러납니다.

폴더를 Domain·Application·Infrastructure로 나누었어도, Domain이 UI의 DTO나 ORM Session을 참조하면 의존성 규칙이 깨집니다. 프로젝트 참조·모듈 공개 범위·정적 검사로 허용 의존성을 확인할 수 있습니다.

모든 매핑을 별도 클래스로 만들어야 하나요?

아닙니다. 변환은 작은 함수나 Adapter 내부 코드일 수 있습니다. 모든 계층에 똑같은 필드의 DTO와 Mapper를 기계적으로 늘리기보다, 의미·변경 이유·외부 자료형의 전파를 기준으로 경계를 둡니다.

검증과 적용 판단

안쪽 규칙의 테스트는 빠르게, 바깥 기술의 검증은 실제 환경에 가깝게 합니다.

대상검증 방법한계·추가 확인
Domain ModelDB 없이 상태 전이·불변식·계산 규칙 검사도메인 객체를 우회하는 쓰기 경로가 없는지 확인
Application ServicesFake Port로 권한·순서·실패·결과 검사Fake는 실제 저장 제약과 동시성을 재현하지 못할 수 있음
Infrastructure실제 DB·API와 계약·매핑·오류 변환 검사트랜잭션·재시도·잠금·Timeout 확인
전체 조립실제 DI 구성과 대표 요청 경로 검사웹·설정·직렬화·인증·권한 경계 확인

업무 규칙이 복잡하고 수명이 긴 애플리케이션에서 도메인의 변경 이유를 분리하는 데 유용합니다. 단순 관리 화면 중심의 CRUD에서는 모델·계약·매핑의 추가 비용이 더 클 수 있습니다. 한 시스템의 필요한 업무 영역부터 적용할 수 있습니다.

다른 아키텍처와의 관계

Onion은 도메인을 중심으로 내부 의존성을 설명합니다.

용어함께 적용하는 방법읽을 때의 주의점
HexagonalUI·DB·메시지를 Adapter로 두고 Port를 핵심이 소유Hexagonal의 Port와 Onion의 계층은 일대일 대응이 아님
Clean ArchitectureDomain과 Application의 정책을 보호Entities·Use Cases라는 용어를 무조건 클래스명으로 복제하지 않음
Modular Monolith / Microservices모놀리스의 모듈 또는 개별 서비스 안에 Onion 적용Onion 계층을 별도 마이크로서비스로 배포할 필요 없음
MVC / EDA / CQRSUI 역할, 메시지 협력, 명령·조회 분리와 결합어느 조합도 트랜잭션·중복·정합성을 자동으로 해결하지 않음
